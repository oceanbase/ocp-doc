# Upgrade OceanBase Database

This topic describes how to upgrade an OceanBase cluster by using OCP. For more information about the upgrade of OceanBase Database, see [Upgrade a cluster](https://www.oceanbase.com/docs/oceanbase-database-cn) on the OceanBase Database documentation page.

## Prerequisites

* Make sure that the current user has the following permissions in OCP:

  * **Cluster Maintenance** resource permission.
  * **<UI-TERM key="ocp-v2.Detail.Overview.Overview">Overview</UI-TERM>** menu permission for the cluster.

* If the OceanBase cluster is of a version earlier than V4.0, you can only upgrade it to a version earlier than V4.0.

* You have uploaded all RPM packages required for the upgrade, such as `oceanbase-x.x.x-YYYYMMDDhhmmss.el7.x86_64.rpm` or `oceanbase-x.x.x-YYYYMMDDhhmmss.el7.aarch64.rpm`, by referencing [Upload a software package](../1500.manage-software-packages/100.upload-a-software-package.md).

* 2F1R (2 full-featured replicas + 1 read-only replica) does not support rolling upgrades. Therefore, for a cluster deployed in the 2F1R mode, you must convert the R replica to an F replica.

* If you want to upgrade a standalone cluster, you have uploaded the LIBS dependency package of the target version by referencing [Upload a software package](../1500.manage-software-packages/100.upload-a-software-package.md).

## Upgrade strategy

* If the cluster to be upgraded is of a version earlier than V4.x, and the cluster has a primary/standby cluster pair, both clusters will be upgraded.

* If the cluster to be upgraded is of V4.x or later, follow the strategy based on the deployment mode:

  * **Primary/standby cascading deployment**

    Upgrade the clusters from the downstream to the upstream. We recommend that you upgrade the cluster where the last standby tenant is located first. This ensures the stability of the data synchronization link and avoids synchronization exceptions caused by version differences.

  * **Primary/standby tenants**

    If the tenants in the two clusters are primary/standby tenants, follow these steps to upgrade the clusters:

    1. Make sure that the tenant types of the two clusters are consistent. Before you start the upgrade, execute the [Daily primary/standby tenant switchover](../1200.manage-disaster-recovery/100.switching-primary-and-standby-tenants/100.daily-active-standby-tenant-switchover.md) operation to ensure that the tenants in the two clusters are both primary tenants or both standby tenants. If the tenant types are already consistent, you can skip this step.

       <main id="notice" type='notice'>
       <h4>Notice</h4>
       <p>This operation will cause a business interruption. We recommend that you configure the Service Name for the primary and standby tenants and set the application reconnection mechanism in advance. </p>
       </main>

    2. Upgrade the cluster where the standby tenant is located. We recommend that you upgrade the cluster where the standby tenant is located first. This is because OceanBase Database supports forward compatibility of CLOG logs. After you upgrade the cluster where the standby tenant is located, the log synchronization mechanism can run normally.

    3. Upgrade the cluster where the primary tenant is located. Upgrade the cluster where the primary tenant is located to ensure that the versions of the two clusters are consistent. We recommend that you minimize the time window during which the versions of the two clusters are inconsistent to reduce the risk of synchronization exceptions.

    4. Reconfigure the primary/standby tenant relationship. After the upgrade is completed, execute the [Daily primary/standby tenant switchover](../1200.manage-disaster-recovery/100.switching-primary-and-standby-tenants/100.daily-active-standby-tenant-switchover.md) operation to reconfigure the primary/standby tenant relationship based on your business requirements. If the tenant types are already consistent, you can skip this step.

       <main id="notice" type='notice'>
       <h4>Notice</h4>
       <p>This operation will cause a business interruption. We recommend that you configure the Service Name for the primary and standby tenants and set the application reconnection mechanism in advance. </p>
       </main>

## Considerations

* You can only upgrade a database to a higher version in the same mode. For example, you can only upgrade a standalone cluster to a higher version of standalone cluster, or a distributed cluster to a higher version of distributed cluster.

* For OceanBase Database V4.2.1 and later, when you use the DBLink feature to access an Oracle database, you must install and configure OCI-12.2 on all OBServer nodes of the cluster. For OceanBase Database V4.2.1 and later, you must also reconfigure the original OCI-11.2 to OCI-12.2 when you upgrade OceanBase Database V4.2.0 and earlier to OceanBase Database V4.2.1 and later. For more information, see [Install and configure OCI](https://www.oceanbase.com/docs/common-oceanbase-database-cn-1000000000641866).

* If you want to change the upgrade order of zones, note the following:

  * OceanBase Database 4.x supports only primary/standby tenants. We recommend that you switch the primary tenant to the same cluster before you start the upgrade to facilitate the cluster upgrade.

  * OceanBase Database 2.x and 3.x support only the upgrade order of zones in the primary cluster. If the cluster has a standby cluster, the standby cluster is upgraded first. The standby cluster is upgraded in the default order and does not stop during the upgrade.

  * After you start the upgrade task of the primary cluster, you must manually confirm whether to continue the upgrade before the task reaches the **Stop Zone** step. For more information about the task process, see [Manage tasks](../1600.system-management-features/600.manage-tasks.md). We recommend that you complete the upgrade as soon as possible to avoid unexpected behavior that may cause upgrade issues.

* Disable DDL operations during the upgrade. If the cluster contains dynamic partition tables, the upgrade may take a long time, resulting in insufficient partitions. Before you start the upgrade, check whether the number of partitions of the relevant tables is sufficient and create partitions in advance.

## Procedure

1. Log in to the OCP console.

2. In the left-side navigation pane, click **<UI-TERM key="ocp-v2.Cluster.Component.WaterLevel.Cluster">Cluster</UI-TERM>**. The **<UI-TERM key="ocp-v2.Cluster.Component.ClusterList.ClusterList">Clusters</UI-TERM>** page automatically appears.

3. On the **<UI-TERM key="ocp-v2.page.OBProxy.ClusterList">Clusters</UI-TERM>** page, find the target cluster and click its name.

4. On the **<UI-TERM key="ocp-v2.src.hook.useMenu.Overview">Overview</UI-TERM>** page of the cluster, click the **...** icon in the upper-right corner and select **<UI-TERM key="ocp-v2.Topo.TopoGraph.UpgradedVersion">Upgrade Version</UI-TERM>**.

   The **<UI-TERM key="ocp-v2.Binlog.Component.UpgradeBinlogModal.UpgradedVersion">Upgrade Version</UI-TERM>** dialog box appears.

   * View the information of the OceanBase cluster to be upgraded, including `Cluster Name:Cluster ID`, OceanBase version, and CPU architecture.

   * Specify whether to perform a major compaction before stopping the process. This action will extend the response time for stopping the process but can significantly shorten the OBServer recovery time.

   * Select an upgrade method based on your business requirements.

     * **<UI-TERM key="ocp-v2.Component.UpgradeDrawer.RollingUpgradeRecommended">Rolling Upgrade (recommended)</UI-TERM>**: This method does not stop the business during the upgrade. We recommend that you choose this method.

     * **<UI-TERM key="ocp-v2.Component.UpgradeDrawer.StopServiceUpgrade">Downtime Upgrade</UI-TERM>**: This method stops the business during the upgrade. We recommend that you choose this method if the number of zones is less than 3. If the number of zones is less than 3, a majority cannot be formed during a rolling upgrade. In this case, we recommend that you choose **<UI-TERM key="ocp-v2.Component.UpgradeDrawer.StopServiceUpgrade">Downtime Upgrade</UI-TERM>**.

   * In the **Upgrade Version** field, select the target OceanBase version.

     <main id="notice" type='explain'>
     <h4>Note</h4>
     <p><ul>
     <li>Standalone clusters support only <b>Stop Service Upgrade</b>.</li>
     <li>You can select only software packages of versions later than the current version.</li>
     <li>After you select a software package version, the system checks whether an installation package of the current cluster's hardware architecture exists. If no installation package of the specified architecture exists, the upgrade cannot be performed.</li>
     </ul></p>
     </main>

   * If **<UI-TERM key="ocp-v2.Component.UpgradeDrawer.UpgradeMethod">Upgrade Method</UI-TERM>** is set to **Rolling Upgrade**, you can adjust the upgrade order of zones.

     By default, the system first upgrades the zone where the RS leader node resides, and then upgrades the other zones in the order specified in the **<UI-TERM key="ocp-v2.Component.ZoneList.ZoneList">Zones</UI-TERM>** section of the **<UI-TERM key="ocp-v2.Cluster.Component.ClusterOverview">Overview</UI-TERM>** page. You can drag the zones to change the upgrade order.

5. Click **<UI-TERM key="ocp-v2.Detail.Component.UpgradeObproxiesModal.Upgrade">Upgrade</UI-TERM>** and check whether all RPM packages in the upgrade path exist.

6. Click **<UI-TERM key="ocp-v2.Oracle.Component.AddObjectPrivilegeDrawer.Determine">OK</UI-TERM>**.

   You can click **<UI-TERM key="ocp-v2.page.Welcome.ViewTasks">View Tasks</UI-TERM>** in the dialog box to view the upgrade progress.

   When the task status is **<UI-TERM key="ocp-v2.Detail.Log.TaskGraph.Complete">Complete</UI-TERM>**, and the status of the cluster in the **<UI-TERM key="ocp-v2.src.constant.tenant.Running">Running</UI-TERM>** column of the **<UI-TERM key="ocp-v2.page.OBProxy.ClusterList">Clusters</UI-TERM>** section on the **<UI-TERM key="ocp-v2.Backup.Overview.Statistics.Cluster">Cluster</UI-TERM>** page is **<UI-TERM key="ocp-v2.src.constant.tenant.Running">Running</UI-TERM>**, the upgrade is successful.

   <main id="notice" type='notice'>
    <h4>Notice</h4>
    <p>OCP does not support rolling back an OceanBase cluster upgrade task. Do not manually skip or roll back the task.</p>
   </main>

7. View the upgrade task.

   An upgrade task generates a main task and multiple subtasks. The main task generates multiple subtasks based on the number of upgrade nodes that require binary file replacement. The subtasks are used to gradually replace the binary files to be upgraded.

   * Main task: Generate a subtask for each upgrade node that requires binary file replacement in the upgrade path. The subtask is used to gradually replace the binary files to be upgraded. For example, `Submit cluster upgrade task` generates a subtask. `Wait dag success` waits for the subtask to complete. The combination of `Submit cluster upgrade task` and `Wait dag success` may be executed multiple times, depending on the number of nodes that require binary file replacement in the upgrade path.

    ![1](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/ocp/%E4%B8%BB%E4%BB%BB%E5%8A%A1.png)

   * Subtask: Upgrade all OceanBase cluster versions. The subtask mainly executes the upgrade script, including the pre-check script, upgrade pre script, OBServer node replacement, upgrade post script, and version check.

    ![2](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/ocp/%E5%AD%90%E4%BB%BB%E5%8A%A1.png)

## What to do next

After the cluster is upgraded, we recommend that you manually initiate a full backup of the cluster. For more information about cluster backup, see [Immediately perform a cluster backup](../1100.backup-and-restoration-functions/400.backup-now/100.back-up-cluster-now.md).
