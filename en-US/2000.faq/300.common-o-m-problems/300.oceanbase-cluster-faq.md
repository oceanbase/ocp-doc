# FAQ about OceanBase clusters

This topic describes the common questions about OceanBase cluster management.

## Feature implementation

**Q1: Can OCP manage OceanBase clusters with ARM architecture in an x86 environment?**

A: Yes, OCP V2.5.2 and later versions support this.

**Q2: Does OCP support a deployment plan where the primary cluster is x86 and the standby cluster is ARM?**

A: Yes, OCP V3.1.0 and later versions support this.

## OceanBase cluster management

**Q1: Where can I view the latency between the primary and standby clusters?**

A: Go to the cluster overview and switch to the cluster topology diagram to view the latency between the primary and standby clusters.

**Q2: How do I handle the task error `machine resource is not enough to hold a new unit`?**

A: The lack of machine resources prevents the migration of replicas from proceeding normally. Add a host to resolve this issue.

**Q3: What is the cleanup strategy for OCP-Agent to automatically clean up observer.log?**

A: When the space utilization reaches 80%, only the most recent 100 log records will be retained.

**Q4: How is the topology diagram status of a cluster obtained?**

A: The status is obtained from the ob_server table in MetaDB.

**Q5: How is the total number of sessions in OCP calculated?**

A: It is queried from the __all_virtual_processlist internal table of OceanBase.

**Q6: What are inactive sessions, and what is the management mechanism?**

A: Sessions that have been connected but have not been operated on for a period of time are considered inactive. By default, sessions that have not been operated on for 28800 seconds are marked as inactive. OceanBase does not actively release connections based on client timeouts.

**Q7: Do inactive sessions consume the maximum number of connections per unit?**

A: The maximum number of connections per unit does not affect the actual allocation of connections. The actual useful limit is the maximum number of connections per OBServer node. OCP uses the unit connection count for alerts.

**Q8: What ports need to be opened if OCP and OceanBase are not in the same network segment?**

A: For details, see [Component listening port list](../../2100.appendix/400.component-listening-port-list.md).

**Q9: How can I quickly delete a cluster that has failed tasks?**

A: Modify the cluster status in the ob_cluster table of MetaDB from `Operating` to `NORMAL`.

**Q10: What does the inspection result description `Number of partitions: unknown > 100000, critical` mean during OceanBase cluster health inspection?**

A: The unknown indicates that the number of partitions could not be retrieved. To locate the issue, follow these steps:

1. Check the **<UI-TERM key="ocp-v2.src.util.menu.TenantManagement">Tenant Management</UI-TERM>** interface for the **Capacity_Region Count** chart in the OceanBase cluster. If no data is displayed, proceed to the next step.

2. Check the **<UI-TERM key="ocp-v2.Host.Detail.OCPAgent.Processes">Processes</UI-TERM>** for the corresponding host. If the obstat and logtailer processes are abnormally stopped, proceed to the next step.

3. This could be due to domain name resolution issues, preventing the host from accessing the database, leading to the failure to start obstat and logtailer.

We recommend configuring the domain name server address in the `/etc/resolve.conf` file on the error host and then checking again.

**Q11: Why can't I execute or abandon the deletion of an OceanBase cluster in OCP?**

A: The user deleted the OBServer cluster host in the OCP console, causing the host to be abnormally offline. The cluster information stored in MetaDB is inconsistent with the OceanBase cluster. If only some OBServer nodes are offline, we recommend that you contact OceanBase Technical Support to manually correct the relevant data in MetaDB before you forcibly delete the cluster.

**Q12: After upgrading OCP, the proxyro password configuration for an OceanBase cluster is lost, making the cluster unavailable and preventing the cluster from being restarted. How do I handle this issue?**

A: Restart OCP.

## OceanBase cluster deployment

**Q1: How do I resolve the error `illegal argument exception` when creating a cluster?**

A: Check whether the RPM package has the same name as another package.

**Q2: Why does the interface show the error `An unknown error occurred. Error reason: {0}. Error message: {1}. Please contact the administrator` when I confirm the submission information during OceanBase installation?**

A: Check whether the name of the OceanBase software package has been modified.

**Q3: The primary cluster is x86, and the host of the standby cluster to be added is AArch64. The standby cluster is deployed with an x86 software package. Is this feasible?**

A: Heterogeneous primary and standby clusters pose risks and are not recommended.

**Q4: Why does an error occur when I create a cluster in OCP and the error message is `zone priority is incorrect`?**

A: At least two zones must exist under the region corresponding to the first-priority zone.

**Q5: Does the creation of a standby database task end when the primary and standby data synchronization ends?**

A: The time when the standby database creation task is completed and the time when the standby database starts synchronization are not directly related. However, the standby database can provide services only after the standby database creation task is completed.

**Q6: Why does an error occur when I create a primary and standby database in OCP V2.5.x and the error message is `Add cluster not allowed` and `CHECK PRIMARY ZONE OR LOCALITY CONFIG`?**

A: The user has configured primary_zone or locality for the table. To resolve this issue, follow these steps:

1. In the OceanBase database of the system tenant, check which tables have configured primary_zone or locality.

   ```sql
   select table_id,tenant_id,primary_zone,locality,table_name from __all_virtual_table；
   ```

   Record the table name as t and the tenant ID as 1001.

2. In the corresponding tenant database, execute `alter table t set primary_zone = default;` to cancel the table-level Primary Zone configuration.

3. In the corresponding tenant database, execute the following statements to cancel the table-level locality configuration.

   ```sql
   select locality from __all_tenant where tenant_id = 1001;     #Record the query result as F@zone1,F@zone2,F@zone3.
   alter table t set locality = 'F@zone1,F@zone2,F@zone3'；
   ```

**Q7: In a private cloud environment with the same network, there is already an OCP that has created an OceanBase cluster. When I deploy another OCP and create an OceanBase V2.2.7x cluster on it, besides modifying the default value of `cluster_id` to `100000` in the `/root/t-oceanbase-antman/obcluster.conf` file during OCP deployment, are there other modifications needed when creating the business cluster?**

A: When you use OCP to create an OceanBase cluster, ensure that the clusterid and clustername values are unique.

**Q8: How do I troubleshoot the failure in the Do io bench substep when creating a cluster?**

A: Observe the error code returned by the `io bench` failure. If the error code is 87, it is usually due to insufficient host resources. Ensure that there is 100GiB of available disk space.

## Take over an OceanBase cluster

**Q1: When you import a cluster, the host preparation task reports the error `python dependency does not exist`. How do I resolve this issue?**

A: The host is not installed by using the installation template. Manually install the Python script. We recommend that you install the host by using the installation template.

**Q2: When you take over a cluster by using OCP V2.5.x, the error `error code:11042 Pre-check for cluster takeover failed. The OBServer node check failed` is returned. How do I resolve this issue?**

A: We recommend that you call the pre-check interface to view the specific reason for the OBServer node check failure. The interface call method is as follows:

```shell
curl -X POST --user admin:xxx \
  -H "Content-Type:application/json" \
  -d '{"rootSysPassword":"xxxxx",                   # Required. The password of root@sys.
         "address":"xxxxx",                                 # Required. The connection address of the cluster.
         "port":2888,                                           # Required. The connection port of the cluster.
         "connectionMode": "proxy"                  # Optional. The connection mode. Valid values: direct and proxy. Default value: direct.
         "clusterName": "xxx",                            # Optional. This parameter is required when the connection mode is proxy.
         "obClusterId": xxx                                 # Optional. This parameter is required when the connection mode is proxy and the cluster to be taken over is a standby cluster.
        }' \
  "http://example.com:8080/api/v2/ob/clusters/takeOverPreCheck"
```

**Q4: What are the considerations for taking over a cluster deployed by using another OCP?**

A: When you take over a cluster deployed by using another OCP, note the following items:

* Confirm the access method to the OceanBase cluster to be taken over and the impact on the business.

* Migrate the cluster to be taken over from the other OCP or stop the other OCP.

* In a single-OCP scenario, take over the primary OceanBase cluster first, and then take over the standby OceanBase cluster.

* In a multi-OCP scenario, take over the primary OceanBase cluster in one OCP first, and then take over the standby OceanBase cluster in any OCP.

## Upgrade an OceanBase cluster

**Q1: How do I upgrade the primary and standby clusters?**

A: On the overview page of the primary and standby clusters, the **<UI-TERM key="ocp-v2.Topo.TopoGraph.UpgradedVersion">Upgrade Version</UI-TERM>** button is displayed in the upper-right corner. You can click the button to initiate an upgrade for the primary and standby clusters.

**Q2: When I upgrade an OceanBase cluster by using OCP, the error `timeout` is returned when the schema info is refreshed. How do I resolve this issue?**

A: Run the following command to view the schema and version:

```code
select tenant_id, refreshed_schema_version from __all_virtual_server_schema_info " + " where svr_ip = '%s' and svr_port = %d and refreshed_schema_version >
select max(value) value from oceanbase.__all_virtual_sys_parameter_stat where name = 'min_observer_version'
```

After you confirm the information, manually retry the `CheckRefreshSchemaTask` task.

**Q3: Why does an error occur when I execute the upgrade checker during the upgrade of an OceanBase cluster?**

A: The error may be caused by the timeout of the RPM package download. We recommend that you retry the upgrade.

**Q4: Why does the error `No corresponding version node` occur when I upgrade an OceanBase V2.2.71 cluster to an OceanBase V2.2.74 cluster?**

A: The upgrade path defined in the `/home/admin/ocp-server/etc/oceanbase_upgrade_dep.yml` file on the OCP server is incomplete. We recommend that you add the OceanBase V2.2.74 version to the upgrade path, as shown in the following example:

```yaml
# The preceding content is omitted.
- version: 2.2.70
  can_be_upgraded_to:
      - 2.2.71
- version: 2.2.71
  can_be_upgraded_to:
      - 2.2.72
- version: 2.2.72
  can_be_upgraded_to:
      - 2.2.73
- version: 2.2.73         # The last version must be defined, otherwise, the upgrade path cannot be found when you upgrade the cluster from the same version. You must define the last version in this way in the future.   Xin Xu
  can_be_upgraded_to:
      - 2.2.74
```

**Q5: What does the message `Need to replace binary` displayed on the upgrade path confirmation page mean?**

A: Replacing the binary file means replacing the OBServer node. You only need to run the pre/post scripts for V2.2.72 and V2.2.73. You do not need to replace the binary file of the OBServer node. This message is only for reference. You do not need to manually perform any operation. The upgrade task will automatically replace the binary file.

**Q6: How do I resolve the error `[alter system stop zone ?]; SQL state [25000]; error code [4012]; Statement is timeout` returned when I upgrade an OceanBase cluster?**

A: We recommend that you retry the upgrade.

**Q7: Why does the upgrade from OceanBase V2.2.30 to OceanBase V2.2.50 fail?**

A: The RPM package of OceanBase V2.2.40, which is required for the upgrade, is not uploaded. We recommend that you upload the RPM package and retry the upgrade.

**Q8: If a customer wants to upgrade the minor version and then the major version, does OCP support the same version upgrade?**

A: Yes. However, the minor version number must be different.

**Q9: When I use OCP to upgrade an OceanBase cluster, the `Install rpm` step fails on one server and the error `Cannot allocate memory` is returned.**

A: The memory is insufficient. We recommend that you clear the memory or expand the memory based on the actual situation.

**Q10: Why does the `upgrade_checker.py` script return the error `MyError: "(1, Decimal('1.0000')) check_logonly_replica_unit failed, not found log_type resource_pool for this tenant` during the upgrade of an OceanBase cluster?**

A: Check whether the OceanBase cluster to be upgraded contains log-only replicas. If yes, we recommend that you replace the log-only replicas with F replicas.

**Q11: How do I upgrade an OceanBase cluster that contains the sys, ocp-meta, ocp-monitor, omsmeta, and odpmeta tenants?**

A: Contact OceanBase Technical Support to obtain the upgrade guide and perform the upgrade. The upgrade of one cluster will not affect the tenants of other applications.

## Monitor an OceanBase cluster

**Q1: Is the ocp_monitor user automatically created when I create a cluster in OCP? What is the default password of this user?**

A: The ocp_monitor user is automatically created. However, the default password of this user is used only when the system calls this user for monitoring. You do not need to be aware of this password.

**Q2: Does the transaction log time in the performance monitoring interface of a cluster refer to the average SQL execution time or the average transaction time?**

A: Transaction.

**Q3: How is the asynchronous log transmission delay between the primary and standby databases in OCP calculated?**

A: The data source of the asynchronous log transmission delay between the primary and standby databases in OCP is as follows:

```sql
SELECT cluster_id, cluster_name, created, cluster_role, cluster_status, current_scn, standby_became_primary_scn, primary_cluster_id, (time_to_usec(now(6)) - current_scn)/1000000 as delay_time FROM oceanbase.v$ob_cluster
```

That is, `(time_to_usec(now(6)) - current_scn)/1000000`, and the unit is seconds.

## Cluster inspection

**Q1: OceanBase Database uses the `/data/1` directory as the data disk, which by default occupies up to 90% of the host disk space. However, the host disk usage threshold for cluster health inspection is set to 85%. Is this setting reasonable?**

A: During health inspection, the inspection of OceanBase data disks is ignored.
