# FAQ about OceanBase clusters

This topic describes common issues related to the management of OceanBase clusters.

## Feature implementation

**Q1: Can OCP in an x86 environment manage an OceanBase cluster in an ARM architecture?**

A: Yes, OCP V2.5.2 and later support this.

**Q2: Does OCP support deploying a primary x86 OceanBase cluster and a standby ARM OceanBase cluster?**

A: Yes, OCP V3.1.0 and later support this.

## OceanBase cluster management

**Q1: Where can I view the latency between primary and standby clusters?**

A: Log in to the cluster overview page, switch to the cluster topology view, and view the latency between the primary and standby clusters.

**Q2: What do I do when an error `machine resource is not enough to hold a new unit` is reported?**

A: The error indicates that the server resources are insufficient to support the replica migration-related maintenance task. You can add a host to resolve the issue.

**Q3: What is the log cleanup strategy of OCP-Agent for observer.log?**

A: When the space utilization reaches 80%, only the last 100 log records are retained.

**Q4: How is the topology status of a cluster obtained?**

A: The status is obtained based on the records in the ob_server table of MetaDB.

**Q5: How is the total number of sessions in OCP calculated?**

A: The total number of sessions is queried from the __all_virtual_processlist internal table of OceanBase Database.

**Q6: What is an inactive session and how is it managed?**

A: A session that is established but has not been operated for a period of time is an inactive session. By default, a session that has not been operated for 28,800 seconds is marked as inactive. OceanBase Database does not actively release the connection but depends on the client to release the connection after the timeout.

**Q7: Does an inactive session occupy the maximum number of connections of a unit?**

A: The maximum number of connections of a unit does not affect the actual number of connections. What really matters is the maximum number of connections of an OBServer. OCP uses the number of connections of a unit to generate alerts.

**Q8: Which ports should be opened if OCP and OceanBase Database are not in the same subnet?**

A: For more information, see [Component listening port list](../../2100.appendix/400.component-listening-port-list.md).

**Q9: What do I do if I want to quickly delete a cluster that has failed some tasks?**

A: Change the cluster status from `Operating` to `NORMAL` in the ob_cluster table of MetaDB.

**Q10: What does the message `Number of zone replicas: unknown > 100000, severe` mean in the health check result description of OceanBase cluster health check?**

A: The unknown indicates that the number of partitions is not obtained. To locate the issue, perform the following steps:

1. Check whether the **<UI-TERM key="ocp-v2.src.util.menu.TenantManagement">Tenant Management</UI-TERM>** page of the **Partition Count** chart in the **<UI-TERM key="ocp-v2.src.util.menu.TenantManagement">Tenant Management</UI-TERM>** section displays related data. The result is that no data is displayed.

2. Check whether the **<UI-TERM key="ocp-v2.Host.Detail.OCPAgent.Processes">Processes</UI-TERM>** list on the corresponding host displays normal processes. obstat and logtailer processes are unexpectedly stopped.

3. The domain name resolution may be incorrect, and the host cannot access the database, which causes obstat and logtailer to fail to start.

We recommend that you configure the domain name server address in the `/etc/resolve.conf` file on the error host and then check again.

**Q11: What do I do if I cannot delete a cluster in OCP?**

A: The user deleted the host of the OBServer cluster in the GUI, which caused the host to be offline and the cluster information stored in MetaDB to be inconsistent with that in OceanBase Database. If most OBServer nodes of the OceanBase cluster are offline, we recommend that you do not forcibly delete the cluster. In this case, contact Technical Support Engineer to manually correct the related data in MetaDB.

## Deploy OceanBase clusters

**Q1: What do I do if an error is returned when I create a cluster?**

A: Check whether the RPM package name is duplicated.

**Q2: What is the reason when an error is returned during the confirmation of the submission information when I install OceanBase?**

A: Check whether the OceanBase package name has been modified.

**Q3: The primary cluster is x86. I want to add an AArch64 host as the backup cluster. The backup cluster uses the x86 package. Is this feasible?**

A: It is risky to deploy heterogeneous primary and backup clusters. Therefore, it is not recommended.

**Q4: What is the reason when an error is returned during the creation of a cluster in the OCP console?**

A: The region of the zone with the highest priority must contain at least two zones.

**Q5: When I create a standby database in the OCP console, does the entire primary-standby synchronization end when the task is completed?**

A: The completion of the standby database creation task does not necessarily mean that the primary-standby synchronization is completed. However, a standby database cannot provide services until the task is completed.

**Q6: When I create a primary and standby database in OCP V2.5.x, I set the tenant and table primary zone to RANDOM. However, an error is returned during the execution of the task: `Add cluster not allowed` and the message `CHECK PRIMARY ZONE OR LOCALITY CONFIG` is displayed. What is the reason?**

A: User tables have primary zones or localities configured. Perform the following operations to modify the configurations:

1. View the tables that have primary zones or localities configured in the OceanBase database of the system tenant.

   ```sql
   select table_id,tenant_id,primary_zone,locality,table_name from __all_virtual_table；
   ```

   Note that the table name is t and the tenant ID is 1001.

2. In the database of the corresponding tenant, execute `alter table t set primary_zone = default;` to cancel the primary zone configuration at the table level.

3. In the database of the corresponding tenant, execute the following statement to cancel the locality configuration at the table level.

   ```sql
   select locality from __all_tenant where tenant_id = 1001;     #Record the query result as F@zone1,F@zone2,F@zone3.
   alter table t set locality = 'F@zone1,F@zone2,F@zone3'；
   ```

**Q7: In the same network environment of a private cloud, an OCP cluster has been deployed to create OceanBase clusters. If I deploy another OCP cluster and create OceanBase V2.2.7x on it, in addition to modifying the `cluster_id` value from its default value of `100000` to `100000` in `/root/t-oceanbase-antman/obcluster.conf` when I deploy OCP, do I need to modify other parameters when I create a business cluster?**

A: When you use OCP to create an OceanBase cluster, make sure that the clusterid and clustername values are unique.

**Q8: What do I do if the Do io bench step fails when I create a cluster?**

A: View the error code returned when `io bench` fails. If the error code is 87, it is usually due to insufficient host resources. Make sure that at least 100 GiB of disk space is available.

## Take over an OceanBase cluster

**Q1: When I import a cluster, the host preparation task reports `python dependency does not exist`. How do I solve this issue?**

A: If the host was not installed using the installation template, manually install the Python script. We recommend that you use the installation template.

**Q2: When I use OCP V2.5.x to take over a cluster, an error is reported: `error code:11042 Take over cluster precheck failed. The failure reason is that the OBServer node check failed`. How do I solve this issue?**

A: We recommend that you call the precheck interface to view the specific reasons for the OBServer node check failure. The method for calling the interface is as follows:

```shell
curl -X POST --user admin:xxx \
  -H "Content-Type:application/json" \
  -d '{"rootSysPassword":"xxxxx",                   # Required. The root@sys password.
         "address":"xxxxx",                                 # Required. The cluster connection address.
         "port":2888,                                           # Required. The cluster connection port.
         "connectionMode": "proxy"                  # Optional. The connection mode. Valid values: direct | proxy. Default value: direct.
         "clusterName": "xxx",                            # Optional. Required when the connection mode is proxy.
         "obClusterId": xxx                                 # Optional. Required when the connection mode is proxy and the target cluster is a standby cluster.
        }' \
  "http://example.com:8080/api/v2/ob/clusters/takeOverPreCheck"
```

**Q4: What are the considerations when other OCP clusters take over an OceanBase cluster?**

A: When other OCP clusters take over an OceanBase cluster, note the following:

* Confirm the access method to the target OceanBase cluster and the impact on the business.

* Migrate the target cluster from other OCP clusters or shut down other OCP clusters.

* In a single OCP scenario, take over the OceanBase primary cluster first, and then take over the OceanBase standby cluster.

* In a multi-cluster OCP scenario, take over the OceanBase primary cluster in one OCP cluster first, and then take over the OceanBase standby cluster in any OCP cluster.

## Upgrade an OceanBase cluster

**Q1: How do I upgrade the primary and standby clusters?**

A: On the overview page of the primary and standby clusters, you can click **<UI-TERM key="ocp-v2.Topo.TopoGraph.UpgradedVersion">Upgrade Version</UI-TERM>** in the upper-right corner. You can upgrade the primary and standby clusters from the upgrade entry of either the primary or standby cluster.

**Q2: What do I do when an error is returned during schema refresh after upgrading OCP to OceanBase cluster?**

A: Run the following command to view the schema and version:

```code
select tenant_id, refreshed_schema_version from __all_virtual_server_schema_info " + " where svr_ip = '%s' and svr_port = %d and refreshed_schema_version >
select max(value) value from oceanbase.__all_virtual_sys_parameter_stat where name = 'min_observer_version'
```

Then manually retry `CheckRefreshSchemaTask`.

**Q3: What does it mean when an error is returned during upgrade checker execution when upgrading an OceanBase cluster?**

A: The RPM package may have been downloaded beyond the time limit. We recommend that you retry.

**Q4: What is the cause of the error `no corresponding version node` when upgrading OceanBase V2.2.71 to OceanBase V2.2.74?**

A: The upgrade path defined in the `/home/admin/ocp-server/etc/oceanbase_upgrade_dep.yml` file on the OCP server is incomplete. We recommend that you add the version information to OceanBase V2.2.74, as shown below:

```yaml
#The preceding content is omitted.
- version: 2.2.70
  can_be_upgraded_to:
      - 2.2.71
- version: 2.2.71
  can_be_upgraded_to:
      - 2.2.72
- version: 2.2.72
  can_be_upgraded_to:
      - 2.2.73
- version: 2.2.73         # The last version must be defined. Otherwise, the upgrade path cannot be found when upgrading to the same version. This definition is also required for the last version in the future.   Xin Xu
  can_be_upgraded_to:
      - 2.2.74
```

**Q5: What does the message `binary replacement is required` mean on the interface for confirming the upgrade path of an OceanBase cluster?**

A: Binary replacement refers to replacing the OBServer node. You do not need to replace the binary file of the OBServer node when upgrading OceanBase from V2.2.72 to V2.2.73. This message is only for your reference. You do not need to manually perform any operations. The upgrade task will automatically complete the replacement.

**Q6: What do I do when an error is returned during OceanBase cluster upgrade?**

A: We recommend that you retry.

**Q7: What is the cause of the error when upgrading an OceanBase cluster from V2.2.30 to V2.2.50?**

A: The RPM package of OceanBase V2.2.40 is not uploaded. We recommend that you upload the RPM package and retry.

**Q8: If a customer wants to upgrade the minor version and then the major version, does OCP support the same version upgrade?

A: Yes, but the minor version number must be different.

**Q9: What do I do when one server fails during the `Install rpm` step when upgrading an OceanBase cluster using OCP, and the error message `Cannot allocate memory` is returned?

A: The memory is insufficient. We recommend that you clear the memory or expand the memory based on the actual situation.

**Q10: What is the cause of the error returned by `upgrade_checker.py` during OceanBase cluster upgrade: `MyError: "(1, Decimal('1.0000')) check_logonly_replica_unit failed, not found log_type resource_pool for this tenant`?

A: Check whether log-only replicas exist in the OceanBase cluster to be upgraded. If so, we recommend that you replace the log-only replicas with F replicas.

**Q11: What do I do if the OceanBase cluster has sys, ocp-meta, ocp-monitor, omsmeta, and odpmeta tenants?

A: Contact OceanBase Technical Support to obtain the upgrade manual and proceed with the upgrade. Upgrading a specific cluster does not affect other application tenants.

## Monitor OceanBase clusters

**Q1: Will the ocp_monitor user be automatically created when a cluster is created in OCP, and what is the default password for this user?**

A: Yes, the ocp_monitor user will be automatically created. However, the default password is only used by the system when this user is called upon during monitoring, and you do not need to be aware of it.

**Q2: On the performance monitoring page of a cluster, does the transaction log latency refer to the average SQL latency or the average transaction latency?**

A: It refers to the average transaction latency.

**Q3: How is the asynchronous log transfer latency between the primary and standby databases of a cluster statistically calculated in OCP?**

A: The data for the asynchronous log transfer latency between the primary and standby databases in OCP is calculated using the following formula:

```sql
SELECT cluster_id, cluster_name, created, cluster_role, cluster_status, current_scn, standby_became_primary_scn, primary_cluster_id, (time_to_usec(now(6)) - current_scn)/1000000 as delay_time FROM oceanbase.v$ob_cluster
```

The formula is `(time_to_usec(now(6)) - current_scn)/1000000`, with the unit being seconds.

## Cluster inspection

**Q1: By default, the /data/1 data disk of OceanBase can occupy up to 90% of the host's disk space, while the host disk usage threshold in cluster health inspection is set to 85%. Is this setting reasonable?**

A: During health inspection, the inspection of the OceanBase data disk is ignored.
