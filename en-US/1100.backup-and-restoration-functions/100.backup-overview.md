# Overview

This topic describes the backup and restore features and the secondary backup feature provided by OCP for OceanBase Database.

## Backup and restore

Backup and restore is a core component of the high availability feature of OceanBase Database. It ensures data security by preventing data loss due to storage medium damage or user errors. If data is lost due to storage medium damage or user errors, the restore feature can be used to recover the user's data.

   <main id="notice" type='explain'>
   <h4>Note</h4>
   <p>Backup is not supported for the sys tenant in OceanBase Database 4.x.
   </p>
   </main>

OceanBase Database currently supports four types of storage media: File (NFS), OSS, OBS, and S3. It provides backup, restore, and management features.

Physical backup consists of baseline data and log archive data. Therefore, physical backup is a combination of log archiving and data backup features:

* Log archiving is the automatic archiving of log data. OBServer nodes periodically archive log data to the specified backup path. This action is fully automatic and does not require external triggering.

* Data backup is the feature for backing up baseline data. This feature includes full backup and incremental backup:

  * Full backup involves backing up all macroblocks that require baseline data.

  * Incremental backup involves backing up macroblocks that were added or modified since the last backup.

OceanBase Database supports tenant-level restore. Restore is the process of rebuilding a new tenant based on existing data backups. The restore process includes the Restore and Recover steps for tenant system tables and user tables. Restore involves restoring the required baseline data to the OBServer nodes of the target tenant. Recover involves restoring the corresponding logs to the corresponding OBServer nodes and replaying them.

### Physical Backup Architecture

The following figure shows the physical backup architecture of OceanBase Database.

![image.tiff](https://help-static-aliyun-doc.aliyuncs.com/assets/img/zh-CN/0082988061/p200031.tiff "image.tiff")

When you log in to the system tenant and initiate log archiving, you need to complete the log archiving before initiating the baseline backup.

Log archiving regularly backs up logs to the backup destination. After the user issues the `alter system archivelog` statement, log archiving continues in the background. Each leader of a partition group (PG) periodically archives logs of the PG to the path specified by the backup media. The root service (RS) periodically records the progress of log archiving and updates the progress to an internal table.

Data backup is a user-triggered process, with typical scenarios such as full backups on Saturdays and incremental backups on Tuesdays and Thursdays. When a user initiates a data backup request, it is first forwarded to the node where the Region Server (RS) resides. The RS generates backup tasks based on the current tenant and the PostgreSQL (PG) instances within it and distributes these tasks to the OBServer nodes for parallel execution. The OBServer nodes are responsible for backing up the metadata and macroblocks of the PG instances to the specified backup directories. Macroblocks are managed at the PG level.

OceanBase Database currently supports using four types of storage media as backup targets: File (NFS), OSS, OBS, and S3. ### Physical Restore Architecture

The following figure shows the physical architecture of physical recovery in OceanBase Database.

![Restore-architecture.png](https://help-static-aliyun-doc.aliyuncs.com/assets/img/zh-CN/0082988061/p200032.png "恢复架构.png")

The visible steps of the process are as follows:

1. In the target cluster, execute the `CREATE RESOURCE POOL` command to create a resource pool for the restore tenant.

2. Run the `ALTER SYSTEM RESTORE TENANT` statement to schedule the tenant restore task.

For backup restore, the internal process for the `restore tenant` command is as follows:

1. Create a tenant for disaster recovery.

2. Restore system table data for the tenant

3. Restore the system table log of the tenant.

4. Modify the metadata of the tenant to be restored.

5. Recover user table data for the tenant

6. Recycle tenant user table logs.

7. Restore the cleanup task.

For an individual partition group, the restoration process involves copying the partition group's metadata and macroblock data to a specified OBServer node to create a partition group with baseline data only, thereby restoring data up to the backup time point. Subsequently, the partition group's logs are copied to the specified OBServer node and replayed into its MemTable, restoring the data to the point in time of the disaster or a user-defined time point. If the volume of logs is significant, this process might trigger a dump operation.

## Secondary backup

<main id="notice" type='explain'>
   <h4>Note</h4>
   <p>OceanBase Database 4.x does not support secondary backup.
   </p>
   </main>

If the backup of an OceanBase cluster is referred to as a regular backup, a secondary backup is a backup of the full data of the regular backup, which is then archived to a storage location different from that of the regular backup. The full data of the regular backup includes baseline data and log archive data.

The purpose of a secondary backup is to reduce the storage pressure of the regular backup. After the backup data on the regular backup storage server is periodically archived to the secondary backup storage directory, the retention period of the regular backup files is shortened, thereby releasing part of the storage space of the regular backup.

At the same time, a secondary backup ensures the recoverability of the OceanBase cluster. If the backup files on the regular backup storage server become inaccessible due to an exception, the secondary backup can still ensure the recoverability of the OceanBase cluster.

You can refer to [Create a tenant-level backup strategy](500.regular-backup/200.manage-tenant-backup-strategy/100.creat-a-tenant-backup-stategy.md) and [Create a cluster-level backup strategy](500.regular-backup/100.manage-cluster-backup-strategy/100.create-a-cluster-backup-strategy.md) to enable and configure a secondary backup. You can refer to [Overview of backup and recovery](../1100.backup-and-restoration-functions/300.backup-and-recovery-overview.md) to view the secondary backup tasks.
