# References about OpenSearch

## Background

To support the full-link tracing feature of OceanBase Database V4.x, OCP V3.3.0 introduces the Data Intelligence feature, which includes full-link tracing and log search functionalities. These features rely on an OpenSearch cluster for data storage and query. In a private cloud scenario, you can also deploy an OpenSearch cluster alongside the OCP cluster. This approach can reduce the deployment learning curve for support personnel.

## Prerequisites

You have planned the resources for the OpenSearch cluster based on **Cluster resource planning**.

## Deploy an OpenSearch cluster

1. Obtain the OpenSearch Docker image on the OCP host. You can run the following command to obtain the image. If you need to download the image, contact the delivery service personnel.

   <main id="notice" type='explain'>
    <h4>Note</h4>
    <p>The latest version of the image is V3.3.2. </p>
   </main>

    ```shell
    docker pull oceanbase/opensearch:3.3.2
    ```

2. Deploy OpenSearch using Docker.

    1. Generate a root certificate.

        ```shell
        cd ${pem-path}
        openssl genrsa -out ./root-ca-key.pem 2048
        openssl req -new -x509 -sha256 -key ./root-ca-key.pem -subj "/C=CA/ST=ONTARIO/L=TORONTO/O=ORG/OU=UNIT/CN=ROOT" -out ./root-ca.pem
        ```

    2. Start the container.

        ```shell
        docker run -d --net host -v ${pem-path}/root-ca-key.pem:/opt/opensearch/config/root-ca-key.pem -v ${pem-path}/root-ca.pem:/opt/opensearch/config/root-ca.pem --env  OPENSEARCH_USERNAME=xxx --env OPENSEARCH_PASSWORD=xxx --env OPENSEARCH_NODE_URLS=ip1,ip2,ip3 --env HOST_IP=xxx.xxx.xxx.xxx --env OPENSEARCH_JVM_HEAP=4g --name ocp-opensearch reg.docker.alibaba-inc.com/oceanbase-platform/ocp-opensearch:3.3.2-x64
        ```

        <main id="notice" type='notice'>
          <h4>Notice</h4>
          <ul>
          <li>The Docker image of OpenSearch must be started in the host network mode.</li>
          <li>The ${pem-path} in the command refers to the directory where the root certificate is stored. </li>
          <li>If you want to mount a host directory to the OpenSearch directory, set the permissions of the mount directory on the host to admin. The uid and gid of the admin user in the container are both 500. If the host admin user ID is different from the container admin user ID, the mounting will fail. In this case, after the container starts, you can execute the <code>chown admin:admin /data/1/opensearch</code> command in the container and then restart the container. </li>
          <li>If you want to deploy OpenSearch in a multi-node mode, copy the root certificate to each node and then start the container on each node. </li>
          </ul>
        </main>

    When you start the image, the following environment variables are provided:

    | Environment variable | Required | Description |
    |---------|--------|-------|
    | OPENSEARCH_USERNAME | Yes | The username of OpenSearch, which is also the username for logging in to cerebro. |
    | OPENSEARCH_PASSWORD | Yes | The password of OpenSearch, which is also the password for logging in to cerebro. |
    | OPENSEARCH_NODE_URLS | Yes | The list of OpenSearch nodes. |
    | HOST_IP | No | The IP address of the host. Please specify the IP address based on the actual situation. If you do not specify the IP address, the system will execute the `hostname -i` command to obtain it. Make sure that `/etc/hosts` is correctly configured. |
    | OPENSEARCH_JVM_HEAP | No | The size of JVM memory of OpenSearch. We recommend that you set it to half of the size of the node memory (max 32 GB). The default value is 4 GB. |
    | OPENSEARCH_HTTP_PORT | No | The port for communication with the external world. The default value is 9200. |
    | OPENSEARCH_TCP_PORT | No | The port for communication between nodes. The default value is 9300. |
    | CEREBRO_PORT | No | The port of cerebro. The default value is 9100. |
    | ELASTICSEARCH_EXPORTER_PORT | No | The port of elasticsearch_exporter. The default value is 9114. |

3. Connect to the OpenSearch cluster from OCP.

    After OCP starts, manually add the OpenSearch address and credentials in **System Parameters**. For more information, see [Configure link query parameters](../1300.log-service/300.configuration-trace-paremeters.md).

    | Parameter | Description |
    |----|----
    |ocp.analyze.es.client.addresses| The IP addresses of the OpenSearch cluster. If multiple client addresses are configured, separate them with commas.   |
    |ocp.analyze.es.client.username| The username of the OpenSearch cluster.   |
    |ocp.analyze.es.client.password| The password of the OpenSearch cluster.     |

## Description of OpenSearch Service

The OCP-OpenSearch Docker image integrates three services: opensearch, elasticsearch_exporter, and cerebro.

### OpenSearch

OpenSearch is a distributed search and analytics engine that is community-driven and built on Apache Lucene. It originated from ES 7.10.2 and uses the Apache License 2.0.
After you add data to OpenSearch, you can perform full-text searches on the data: search by field, across multiple indexes, boost fields, rank results by score, sort results by field, and aggregate results.

### elasticsearch_exporter

elasticsearch_exporter is an exporter that uses the Prometheus format to export various metrics of OpenSearch. It has been integrated into ocp_prometheus. The software uses the Apache License 2.0.
You can use elasticsearch_exporter to obtain monitoring data of OpenSearch, including index performance, JVM memory usage and garbage collection, cluster health and node availability, system and network metrics.

### cerebro

cerebro is an OpenSearch management tool. You can perform O&M operations on OpenSearch through a web interface. It supports operations such as index creation and deletion, and cluster configuration parameter modification. The software uses the MIT License 2.0.

### Log location

The log directory is: `/home/admin/logs`.

## Estimate the specifications of an OpenSearch cluster

### Disk space

The disk space required for an OpenSearch cluster is affected by the following factors:

* The number of replicas.
* The overhead of indexes: typically 10% larger than the source data.
* The operating system: 5% of the space is reserved by default.
* The overhead of OpenSearch: 20% of the space is reserved for internal operations such as segment merging and logging.
* The security threshold: at least 20% of the space is reserved.

The minimum disk size = source data size × (1 + number of replicas) × 1.7. You can use this formula to control the disk space.

### CPU and memory

OpenSearch consumes relatively little CPU for data processing. It requires a significant amount of memory, preferably 16 GB, 32 GB, or 64 GB, or half of the available system memory, whichever is smaller.

### Shard assessment

The size and number of shards are important factors affecting the stability and performance of an OpenSearch cluster.

We recommend that you allocate shards in the following way:

* Before you allocate shards, test OpenSearch. When a large amount of data is to be written, reduce the size of written data to alleviate the pressure on OpenSearch. We recommend that you use more than one primary shard and one replica shard in this case. When a small amount of data is to be written and the write frequency is low, you can use one primary shard and multiple replica shards.
* We recommend that you keep the size of a shard (including all replica shards) within 30 GB (optimal) or 50 GB (maximum). A shard that is too large or too small will cause performance issues. If a shard is too large, the recovery of the shard after an error will be slow. If a shard is too small, a large number of shards will be generated. Each shard will use a portion of the CPU and memory resources. This will result in poor read/write performance and insufficient memory.
* We recommend that you set the number of shards (including all replica shards) to be equal to or a multiple of the number of data nodes so that the shards can be evenly distributed across all nodes. This will facilitate load balancing.

### Disk requirements for an OB OpenSearch cluster

Each observer node generates about 6 to 8 GB of logs per day. The trace feature is under development and can be temporarily counted as 8 GB. By default, data is retained in OpenSearch for one week. Therefore, an observer node requires 380 GB of disk space for OpenSearch if it has one replica shard and the data is retained for seven days. The following table shows the specifications of an OpenSearch cluster based on these assumptions:

| Number of observers | Size of the OpenSearch cluster | Specifications of a node | Disk space |
|---------------|------------|---------|----------|
| 20 | 4 | 8-core 32 GB | 2 TB |
| 50 | 10 | 8-core 32 GB | 2 TB |
| 200 | 20 | 16-core 64 GB | 4 TB |
| 400 | 40 | 16-core 64 GB | 4 TB |
