# Configure cgroups

This topic describes how to configure cgroups for OceanBase Database.

## Background information

In the current version of OceanBase Database, tenant work threads and most background threads are tenant-based, while network threads are shared. You can use cgroup to control the CPU and IOPS resources of a tenant. Before you configure cgroup, we recommend that you understand the concept of cgroup. For more information, see [Overview of resource isolation](../700.tenant-functions/1250.manage-resource-isolation/100.resource-isolation-overview.md).

## Limitations and considerations

* We recommend that you do not use the cgroup feature to isolate resources of a tenant in the following scenarios, because resource isolation has a significant impact on performance:

  * Single-tenant scenario: only one tenant exists in the cluster.

  * Scenario where tenants are interdependent: for example, different microservices are deployed in different tenants, and the tenants are upstream and downstream of each other.

  * Small-tenant scenario: tenants with 2 or 4 CPU cores.

* To use the cgroup feature, the Linux kernel version must be 4.19 or later.

* After OceanBase Database is upgraded, you must reconfigure cgroup.

* If the OBServer node restarts, the cgroup subdirectories created in the `/sys/fs/cgroup/` directory will be cleared. You must reconfigure cgroup.

## Procedure

### Step 1: Configure a directory for cgroup

<main id="notice" type='notice'>
<h4>Note</h4>
<ul>
<li>Configuring the cgroup system directories can be done either before or after the installation of OceanBase Database. This topic provides step-by-step guidance for configuring the cgroup system directories based on the assumption that OceanBase Database is already installed.
<li>Configure the cgroup system directories with <code>root</code> user privileges.</li>
</ul>
</main>

This example shows how to configure a cgroup on a single OBServer node. If you have multiple OBServer nodes, you need to configure cgroups on each of them.

1. Log in to the OBServer server as the `admin` user.

2. Run the following command to mount the `/sys/fs/cgroup` directory.

   <main id="notice" type='explain'>
   <h4>Notes</h4>
   <p>If the <code>/sys/fs/cgroup</code> directory already exists, you can skip this step.</p>
   </main>

   ```shell
   [admin@xxx /]$ sudo mount -t tmpfs cgroups /sys/fs/cgroup
   ```

   In this example, `cgroups` is the custom name, used to identify the Mount information.

   The mounting result is as follows:

   ```shell
   $df
   Filesystem      1K-blocks       Used Available Use% Mounted on
   /               293601280   28055472 265545808  10% /
   /dev/v01d      2348810240 2113955876 234854364  91% /data/1
   /dev/v02d      1300234240 1170211208 130023032  91% /data/log1
   shm              33554432          0  33554432   0% /dev/shm
   /dev/v04d       293601280   28055472 265545808  10% /home/admin/logs
   cgroups         395752136          0 395752136   0% /sys/fs/cgroup
   ```

3. Create the `/sys/fs/cgroup/cpu` directory and modify the owner, then mount the cpu subsystem.

   <main id="notice" type='explain'>
   <h4>Note</h4>
   If the <code>/sys/fs/cgroup/cpu</code> directory already exists and is empty, you can skip this step.
   </p>
   </main>

   ```shell
   [admin@xxx /]$ sudo mkdir /sys/fs/cgroup/cpu

   [admin@xxx /]$ sudo chown admin:admin -R /sys/fs/cgroup/cpu
   ```

   Create a `cpu` hierarchy and attach the `cpu` subsystem to it. Mount the hierarchy to the `/sys/fs/cgroup/cpu` directory.

   ```shell
   [admin@xxx /]$ sudo mount -t cgroup -o cpu cpu /sys/fs/cgroup/cpu
   ```

4. Create a subdirectory named `oceanbase` and change its owner to `admin`.

   ```shell
   [admin@xxx /]$ sudo mkdir /sys/fs/cgroup/cpu/oceanbase

   [admin@xxx /]$ sudo chown admin:admin -R /sys/fs/cgroup/cpu/oceanbase
   ```

5. Allocate the CPU and memory resources to the `oceanbase` directory.

   1. Run the following command to view the mounting status of the cpu, cpuacct, and cpuset subsystems on the host.

      ```shell
      [admin@xxx /]$ ll /sys/fs/cgroup
      ```

   2. Choose an operation based on the mount status of the subsystem:

      * The cpuset subsystem is mounted together with the cpu and cpuacct subsystems.

         In this scenario, typically, three sub systems are mounted in the same directory. For example, the mounting result is as follows:

         ```shell
         drwxr-xr-x 3 root root 0 Jul 24 2020 blkio
         lrwxrwxrwx 1 root root 33 Jul 24 2020 cpu -> /sys/fs/cgroup/cpuset,cpu,cpuacct
         lrwxrwxrwx 1 root root 33 Jul 24 2020 cpuacct -> /sys/fs/cgroup/cpuset,cpu,cpuacct
         lrwxrwxrwx 1 root root 33 Jul 24 2020 cpuset -> /sys/fs/cgroup/cpuset,cpu,cpuacct
         drwxr-xr-x 4 root root 0  Jul 24 2020 cpuset,cpu,cpuacct
         ```

         For this scenario, you need to execute the following commands to allocate CPU and memory resources to the `oceanbase` directory.

         ```shell
         [admin@xxx /]$ sudo sh -c "echo `cat /sys/fs/cgroup/cpu/cpuset.cpus` > /sys/fs/cgroup/cpu/oceanbase/cpuset.cpus"

         [admin@xxx /]$ sudo sh -c "echo `cat /sys/fs/cgroup/cpu/cpuset.mems` > /sys/fs/cgroup/cpu/oceanbase/cpuset.mems"
         ```

      * The cpuset subsystem is mounted separately from the cpu and cpuacct subsystems.

         In this scenario, the cpuset subsystem is mounted separately from other subsystems such as cpu and cpuacct (which are usually not mounted because an ECS instance typically runs only one process). The mounting result is as follows:

         ```shell
         drwxr-xr-x 2 root root 40 Feb 27 15:27 blkio
         lrwxrwxrwx 1 root root 11 27 Feb 15:27 cpu -> cpu,cpuacct
         lrwxrwxrwx 1 root root 11 27 Feb 15:27 cpuacct -> cpu,cpuacct
         drwxr-xr-x 2 root root 40 Feb 27 15:27 cpu,cpuacct
         drwxr-xr-x 2 root root 40 27 Feb 15:27 cpuset
         ```

         For this scenario, you do not need to perform any extra steps. Proceed directly to the next step.

6. Run the following command to set the subdirectory inheritance attribute for the `oceanbase` directory.

   ```shell
   [admin@xxx /]$ sudo sh -c "echo 1 > /sys/fs/cgroup/cpu/oceanbase/cgroup.clone_children"
   ```

   After the command is successfully executed, the subdirectories created in the `oceanbase ` directory inherit the properties of the parent directory.

### Step 2: Set up a symbolic link to OceanBase Database

After the cgroup system directory is configured, you need to establish soft links between the installation directory of OceanBase Database software and the cgroup system directory.

1. Log in to the OBServer node as the `admin` user.

2. Create symbolic links from the directory where the OceanBase Database software is installed to the cgroup system directory.

   ```shell
   [admin@xxx /home/admin]$ cd /home/admin/oceanbase/

   [admin@xxx /home/admin]
   $ ln -sf /sys/fs/cgroup/cpu/oceanbase/ cgroup
   ```

   In this example, `/home/admin/oceanbase/` is the installation directory for OceanBase Database.

   After the execution, the result is as follows:

   ```shell
   [admin@xxx /home/admin/oceanbase]
   $ll cgroup
   lrwxrwxrwx 1 admin admin 29 Dec  8 11:09 cgroup -> /sys/fs/cgroup/cpu/oceanbase/
   lrwxrwxrwx 1 admin admin 29 Dec  8 11:09 cgroup -> /sys/fs/cgroup/blkio/oceanbase/
   ```

### Step 3: Enable the cgroup feature

OceanBase Database uses the cluster-level parameter `enable_cgroup` to control whether to enable cgroup for OBServer nodes. By default, this parameter is set to `True`, indicating that cgroup is enabled. After creating a symbolic link and enabling cgroup, there is no need to restart the OBServer node for cgroup to take effect.

If cgroup is not enabled, you can follow the instructions below to enable cgroup.

1. Log in to the `sys` tenant of the cluster as the `root` user.

2. Run the following command to enable the cgroup feature.

   ```shell
   obclient> ALTER SYSTEM SET enable_cgroup = true;
   ```

   Or:

   ```shell
   obclient> ALTER SYSTEM SET enable_cgroup = 1;
   ```

## What to do next

After you configure the cgroup system directory and enable the cgroup feature, you can control the CPU resource usage of a tenant by modifying the `cpu.cfs_period_us`, `cpu.cfs_quota_us`, and `cpu.shares` files in the directory of the tenant in an emergency. We recommend that you do not use this method to isolate resources.

We recommend that you use the `CREATE_CONSUMER_GROUP` subprogram in the `DBMS_RESOURCE_MANAGER` system package to create a resource group by using the directory files in cgroup. You can use the resource group to isolate resources at the user level or SQL statement level. For more information, see [Create a resource group](../700.tenant-functions/1250.manage-resource-isolation/200.create-a-resource-group.md) and [Create a resource isolation plan](../700.tenant-functions/1250.manage-resource-isolation/300.create-a-resource-isolation-plan.md).
