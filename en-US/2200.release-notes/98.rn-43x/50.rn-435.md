## V4.3.5

OCP V4.3.5 is officially released and is fully compatible with OceanBase Database V4.3.5. This version introduces the key feature of high availability for arbitration services, ensuring continuous and stable service provision by OceanBase Database. Additionally, this version supports monitoring capabilities for OBKV-Redis and includes over 20 improvements and optimizations in areas such as basic O&M, performance monitoring, inspection services, and platform features. These enhancements significantly improve the usability of the product, enabling users to more easily and efficiently manage OceanBase Database.

### Key features

#### High availability of arbitration service

OceanBase Database V4.1 provides arbitration service. The arbitration service is characterized by low resource consumption and strong support for multiple clusters. It successfully creates a more cost-effective high availability solution for OceanBase Database, such as the 2F1A or 4F1A architecture. This architecture allows enterprises to effectively control resource costs while ensuring excellent high availability of the database system, greatly improving the cost-effectiveness of the system. However, it is important to note that the arbitration service has a single point of failure. If the arbitration service fails, the high availability of the OceanBase cluster will degrade during the failure period, which may negatively impact the continuity and stability of the business. To address this challenge, the system builds an arbitration service group. When an arbitration service node in the group fails and meets the replacement conditions, the system can quickly switch the relevant cluster to another healthy arbitration service node within seconds. This ensures the stable operation of the OceanBase cluster under various complex conditions and prevents any impact on the business.

**Usage notes**:

* The versions of arbitration services in the same arbitration service group must be consistent.
* An arbitration service group must contain at least two arbitration service addresses.
* After an arbitration service group switches to another arbitration service node, you must reconfigure the association between the cluster and the arbitration service group based on the actual business situation to avoid overloading of the arbitration service.
* Arbitration service group and plan: When the OBServer process of an arbitration service exits abnormally and is restarted, there is no functional conflict. That is, when an arbitration service fails, it can be automatically restarted by a plan, and it will also be replaced if it meets the replacement conditions of the arbitration service group.
* You can create, upgrade, edit, and delete an arbitration service group.

#### Optimization of backup strategies for OceanBase Database 4.x

* Cluster backup strategy supports batch operations on tenant backup strategies:

  * A cluster-level backup strategy takes effect only for tenants that do not have a tenant-level backup strategy.
  * When you delete a cluster backup strategy, the system deletes the cluster and tenant backup strategies by default and disables tenant-level log backup.

* You can disable log backup in a cluster or tenant backup strategy. By default, the system enables log backup before data backup and disables log backup after data backup. This mainly solves the problem of excessive log backup in some business scenarios.
* The enable/disable log backup behavior in a cluster or tenant backup strategy has the highest priority. Even if you manually disable or enable log backup, the system will enable or disable log backup based on the backup strategy.
* When you edit a cluster or tenant backup strategy, the storage configuration is grayed out by default. That is, you cannot change the storage path or the AccessKey and SecretKey of the corresponding object storage service. This prevents log archiving or data backup from failing.
* If no cluster or tenant backup strategy exists, the system records the log backup enable status. If log backup is not enabled, the system enables log backup before data backup and disables log backup after data backup when you manually initiate a backup. If log backup is already enabled, it remains enabled after data backup.

## Limitations

### Hardware requirements

OCP-Server can be installed on a physical server or in a Docker container. OCP-Server supports multi-node high-availability deployment.

The following table lists the minimum hardware requirements for OCP-Server nodes.

| Hardware | Requirement                 |
|-------|------------------------------------|
| CPU  | <li>X86_64, 8 cores</li><li>ARM aarch 64 architecture, 8 cores</li> |
| Memory | 16 GiB of available memory             |
| NIC | 10 GbE NIC                |

OCP-Agent consumes very few resources and has no special requirements for the hardware resources of the installation node.

### Operating system requirements

The following table lists the operating system requirements for installing OCP-Server (including OCP-Agent).

| Server type    | Operating system    | Supported version   |
