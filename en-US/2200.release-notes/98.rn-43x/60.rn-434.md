# OCP V4.3.4

OCP 4.3.4 has been officially released, with the main focus on optimizing the organization role permission model to enhance the overall security of the system.

## Version information

* **Version:** V4.3.4

* **Previous version:** V4.3.3 BP1

* **Version release date:** January 14, 2025

* **Supported upgrade path:**

  * You can directly upgrade from OCP V3.2.4 and later to the current version.

  * For OCP V2.3.x and later, V3.2.4 and earlier, you must first upgrade to OCP V3.3.4.

  * For OCP V2.3.0 and earlier, you must first upgrade to OCP V2.3.x, and then to OCP V3.3.4.

## New features

* **Optimized role and permission model**

    OCP has built a three-tier user management system (system administrator > organization administrator > user) and a dual-dimensional permission control system (resources & menus). This allows for flexible resource sharing between organizations and enables tenant sales in private clouds, resource isolation between organizations/departments, and permission isolation between users within the same organization. This helps users more effectively manage system permissions and enhances overall system security.

* **Support for managing multiple instances on a single host**

    OCP now supports managing multiple Docker instances on a single host (Host mode). This allows for deeper utilization of hardware resources in large-scale machines, maximizing hardware resource usage. A new system parameter `ocp.agent.use.specific.http.ip` has been added to control whether OCP Agent uses the IP address allocated to Docker (default value: `false`).

* **Enhanced Binlog service foundation**

    OCP now fully supports Binlog service upgrades, ensuring comprehensive coverage of basic management capabilities. This guarantees the efficiency and stability of the service.

## Key feature interpretation

### Optimized role and permission model

OCP has built a three-tier user management system (system administrator > organization administrator > user) and a dual-dimensional permission control system (resources & menus).

System administrators have full permissions over resources and menus across the entire system. Organization administrators have full control over resources and menus within their respective organizations. Users can only perform limited operations based on the permissions assigned to their roles. The system focuses on resource (including OceanBase clusters, tenants, OBProxies, hosts, and Binlog services) and menu (minimum level set to second-level menus, such as Cluster or Cluster > Overview) permissions. System administrators or organization administrators can create roles with specific resource and menu permissions and assign them to users, granting them access to corresponding resources and menus. If a role only has partial permissions (either resource or menu), users with that role will not be able to use the system. For example, if a role has resource permissions for a specific cluster but lacks menu permissions, users with that role will not be able to view the cluster page. Similarly, if a user has only menu permissions for a cluster but lacks actual cluster permissions, they will not be able to operate on the cluster. Additionally, OCP supports flexible resource sharing between organizations. The organization administrator of the shared resources can grant these shared resources to corresponding roles and users within their organization.

Through deep optimization of the permission model, OCP effectively supports the following key business scenarios:

* Tenant sales: Ensures compliance and security in the sales process through fine-grained permission settings.
* Multi-organization permission isolation: Ensures independence and autonomy in resource usage and management across organizations, avoiding cross-permission interference.
* Role-based access control for DBAs, developers, and auditors: Clearly defines the boundaries of permissions for different role groups, providing rigorous and efficient permission management for database operations, development, and auditing.

**Usage notes**

* OceanBase clusters, tenants, and corresponding hosts have a hierarchical permission relationship.
* Users with tenant permissions have read-only permissions for the cluster by default.

**Limitations**

* Do not grant the task center, alert center, parameter templates, and tag features to organization administrators or regular users.
* Ensure that names such as usernames, role names, cluster names, tag names, monitoring dashboards, alert templates, and incident response plans are unique across the entire system.
* This version has restructured the permission model. Historical custom roles cannot be automatically compatible. You need to refer to [User Management](../../1600.system-management-features/200.manage-users/50.user-management-overview.md) to reconfigure the permissions for custom roles.

## Fixed issues

OCP V4.3.4 fixes the following issues:

* Fixed the issue where OAS transaction data collection was incomplete when there were a large number of concurrent transactions.
* Fixed the issue where Oracle standby tenants could not select parameter templates.
* Optimized the standardization process for hosts and supported more automatic repair scenarios.

## Limitations

### Hardware requirements

OCP-Server can be installed on a physical server or in a Docker container. OCP-Server supports multi-node high-availability deployment.

The following table lists the minimum hardware requirements for OCP-Server nodes.

| Hardware | Requirement |
|-------|------------------------------------|
| CPU  | <li>X86_64, 8 cores</li><li>ARM aarch 64 architecture, 8 cores</li> |
| Memory | 16 GiB of available memory             |
| NIC | 10 GbE NIC                |

OCP-Agent consumes very few resources and does not have special requirements for the hardware resources of the installation node.
