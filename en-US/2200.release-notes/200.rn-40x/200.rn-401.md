## Version information

* **Version:** V4.0.1

* **Previous version:** V4.0.0

* **Version release date:** December 28, 2022

* **Supported upgrade path:** For OCP versions earlier than V2.3.0, you must first upgrade to V2.3.x, then upgrade to V3.3.4, and finally upgrade to the current version. For OCP versions V2.3.x and later but earlier than V3.2.4, you must first upgrade to V3.3.4 and then upgrade to the current version. For OCP versions V3.2.4 and later, you can directly upgrade to the current version.

## New features

### Overview

As OCP manages more objects and provides more features, important and frequently accessed information is scattered across different modules, requiring manual aggregation and organization. To address this, OCP introduces the new **<UI-TERM key="ocp-v2.Detail.Monitor.Monitor.Overview">Overview</UI-TERM>** module, offering a global perspective on the resources managed by OCP. After opening the OCP homepage, you can instantly access information about resource status, consumption, and performance.

* **Status Overview**

  * Monitor the status of OceanBase clusters, tenants, OBProxy clusters, and hosts, and mark abnormal resources.
  * Monitor the status of alerts, backups, O&M tasks, and major compactions to understand global task information.
  * Statistically analyze SQL, session, transaction, and security diagnostic information to identify performance risks.

* **Resource Overview**

  * Display the top 5 clusters' CPU, memory, and disk allocation, highlighting clusters with high resource allocation.
  * Display the top 5 tenants' CPU, memory, and data usage, highlighting tenants with high resource consumption.

* **Performance Overview**

  * Support performance monitoring metrics for OceanBase clusters, tenants, OBProxy clusters, and hosts.
  * Support viewing top 5 performance metrics by cluster or tenant, and by all clusters or specified clusters.

### Diagnostics

The **<UI-TERM key="ocp-v2.page.Overview.SafetyDiagnosis">Safety Diagnostics</UI-TERM>** module now includes two new sections: **<UI-TERM key="ocp-v2.page.Diagnosis.HighRiskSql">High Risk SQL</UI-TERM>** and **<UI-TERM key="ocp-v2.src.constant.sqlDiagnosis.AddSql">New SQL statement</UI-TERM>**.

* High-Risk SQL: Helps identify high-risk SQL statements based on various rules, including DDL operations, updates, deletes, and queries that return excessive records. It also includes full-table updates and deletes that may harm data security and system stability.
* New SQL: Aggregates statistics for SQL statements that have not been executed in the past 7 days, helping to identify potential performance risks early.

The **<UI-TERM key="ocp-v2.page.Iframe.SqlDiagnosis">SQL Diagnostics</UI-TERM>** module now includes SQL comparison capabilities.

OCP already supports TopSQL in the SQL diagnostics section. You can analyze SQL information over a period of time based on various dimensions such as total execution time, execution count, and average response time, and sort the SQL statements to identify those that consume the most resources and require the most attention during that period. However, in daily O&M, changes in data may be important to monitor, such as differences at the same time point within a week or between different time periods. OCP now supports comparing TopSQL across different time periods, displaying performance trends during the comparison period, and identifying SQL execution changes that require attention based on specific rules such as new TopSQL, execution count, returned rows, failure rate, and execution plan ratio.

Additionally, along the **Discovery > Diagnostics > Optimization > Emergency** path, OCP integrates the capabilities of alerts, monitoring, diagnostics, and logs.

Clicking this button will take you to the SQL diagnostics page. After selecting a time range and clicking **<UI-TERM key="ocp-v2.Detail.SQLDiagnosis.Query">Search</UI-TERM>**, you can view SQL execution details for that period.

### Tenant Backup

OCP V4.0.0 supports setting backup strategies for clusters based on tenant dimensions. You can set different backup strategies for tenants based on their importance, including cycle and backup method. Additionally, you can set backup strategies at the cluster level (only effective for tenants without tenant-level backup strategies), meeting more configuration needs.

1. You can set backup strategies for individual or multiple tenants without setting a cluster-level backup strategy.
2. You can set backup strategies for specific tenants even if a cluster-level backup strategy is already in place.

### Alerts

OCP's alerting capabilities are a core enterprise-level feature, providing timely and secure early warning for clusters and related objects. To enhance the O&M experience, reduce the complexity of alert configuration, and better support delivery services, OCP V4.0.1 has comprehensively optimized the alerting feature, simplified the original alert configuration process, and enhanced alerting capabilities, allowing you to configure alerts through the platform.

* **Enhancements**
  * Added multi-metric alert configuration, supporting the combination of multiple different metrics using **"AND"** or **"OR"**.
  * Added alert templates, allowing you to set multiple alert rules for alert objects and providing default alert templates for your use.
  * Added alert suppression by tag, supporting the suppression of alerts based on specific tags (such as SQLID or session ID) for more precise alert suppression.
  * Added DingTalk, WeCom, Feishu, and email alert channels, with simple configuration requiring only two forms to complete the channel setup.
* **Configuration Optimizations**
  * Alert Events
    * Removed the original alert message module, allowing you to view alert message records in the alert events.
    * SQLID in alert events can be linked to the diagnostics page.
  * Alert Rules
    * Supports keyword alerts for more log types, such as OceanBase logs, OBProxy logs, and host logs.
    * Default alert rule configurations support adjusting alert objects.
  * Alert Channels
    * DingTalk and WeCom alert channels support configuring reminders (@) for specific users in the group.
    * Alert channel configurations support setting alert message templates in different languages, with the option to select a specific language for alert messages.
    * Alert channels support configuring JSON-formatted alert messages.
  * Alert Push
    * Adjusted the original **Alert Subscription** feature to **<UI-TERM key="ocp-v2.page.Alarm.AlertPush">Alert Push</UI-TERM>**, supporting alert information push by alert group or alert template, with the ability to specify alert objects for alert group pushes.
    * Supports selecting whether to receive alert recovery notifications during alert push configuration.
  * Other
    * Supports reverse filtering rules for alert object selection, where certain specific objects do not apply to all alert objects.

### Inspection

To make it easier for you to use the inspection feature and have a clear understanding of the risks of the resources you manage, OCP V4.0.1 has redesigned the inspection feature. It combines the original health check and inspection capabilities and adds a large number of inspection rules based on survey feedback. From the perspective of inspection objects, it supports different scenarios for inspection.

* **<UI-TERM key="ocp-v2.Inspection.Task.InspectionObject">Inspection Objects</UI-TERM>**: The inspection operation starts with the object, making the operation simpler and clearer.
  * You can define inspection items for each OceanBase cluster, tenant, and OBProxy cluster.
  * You can initiate an inspection for a single object or for all objects.
* **<UI-TERM key="ocp-v2.Report.Inspection.ReportContent.InspectionScenario">Inspection Scenario</UI-TERM>**: Three inspection scenarios are preset, and different inspection items are matched for different scenarios.
  * Basic inspection: Basic health checks for resources managed by OCP. It is suitable for routine inspections.
  * Performance inspection: Checks for performance fluctuations and anomalies in resources managed by OCP. It is suitable for performance analysis.
  * Deep inspection: In-depth checks for resources managed by OCP to discover hidden risks. It is suitable for inspections before business peak hours.
* **<UI-TERM key="ocp-v2.Inspection.Item.ConfigRule.SchedulingRules">Scheduling Rules</UI-TERM>**: Each object and its corresponding inspection scenario support different scheduling rules.
  * You can configure the scheduling cycle in terms of days, weeks, or months.
* **<UI-TERM key="ocp-v2.page.Report.InspectionReport">Inspection report</UI-TERM>**: A detailed inspection report is generated for each inspection task for your analysis.
  * The inspection report is set based on the inspection item rules. It checks and highlights low, medium, and high-risk items.
  * The inspection report supports online viewing and download to your local device.

## Feature improvements

### Cluster management

* When you create a cluster, you can specify the SQL port and RPC port.
* When you create a cluster of V2.2.77, you can use a recommended parameter template.
* When you create a cluster, you can check the IOPS of 16 KB I/O blocks. If the IOPS is less than 1000, an exception is thrown.
* You can deploy a cluster in a heterogeneous manner at the zone level. That is, you can deploy a cluster with both x86 and ARM nodes.
* You can perform an in-place reinstallation of an OBServer node. This feature is called **<UI-TERM key="ocp-v2.src.constant.oceanbase.Reload">Reinstall</UI-TERM>**.
* When you replace an OBServer node, you can skip the cleanup of offline hosts.
* When you replace or add an OBServer node, you can select only nodes in the same IDC.
* You can query the names of multiple clusters in the cluster list.
* The primary/standby cluster display mode in the cluster list is changed to a flat display mode.
* You can view the **Modified** parameters in the cluster parameter management page. You can also filter the **Read-only** parameters.

### Tenant management

* When you create or manage a tenant, you are prompted of the minimum resource specifications that can be used for a unit.
* When you create a tenant, you are prompted of the risks if the unit specifications and quantities differ between zones.
* The concept of overselling is removed from the tenant unit management. You do not need to set the minimum and maximum values of the CPU and memory.
* You can query the names of multiple tenants in the tenant list.
* The **<UI-TERM key="ocp-v2.Information.Detail.CollectDetails.TenantId">Tenant ID</UI-TERM>** column is added to the tenant management list.
* You can view the **Modified** parameters in the tenant parameter management page. You can also filter the **Read-only** parameters.
* The issue that the `lower_case_table_names` parameter cannot be set for a MySQL tenant is fixed.

### Host management

* You can query the IP addresses of multiple hosts in the host list. You can also filter the hosts by host type, IDC, or service.
* The host information includes the CPU chip name, number of CPU cores, and total memory.
* Clock offset checks are enabled by default when you add a host.

### OBProxy

* You can specify the password of a Proxyro node in an OBProxy cluster.
* The status column is added to the OBProxy cluster list to display the cluster status.
* The restriction that an OBProxy cluster cannot be upgraded if the hardware architectures of the nodes in the cluster are inconsistent is removed.
* The **<UI-TERM key="ocp-v2.src.hook.useMenu.RequestAnalysis">Request Analysis</UI-TERM>** menu is added. You can use this menu to count the number of requests of a cluster, a tenant, or a client.
* The best practice parameters are used by default when you deploy an OBProxy cluster.

### Monitoring

* The default sampling frequency of OCP monitoring is changed from 1 second to 5 seconds.
* The **<UI-TERM key="ocp-v2.Compaction.Detail.CpuAndMemoryChart.CpuUsage">CPU Utilization</UI-TERM>** chart of a tenant is changed to the **<UI-TERM key="ocp-v2.src.constant.monitor.TenantCpuConsumption">CPU Consumption of Tenant</UI-TERM>** chart.
* The I/O usage rate and I/O queue length charts are added to the host monitoring. The CPU usage rate chart is extended to support the monitoring of the system, user, and I/O wait time.

### Others

* OCP supports the HTTPS authentication protocol to meet the requirements of the Level 3 information security protection standard.
* The **<UI-TERM key="ocp-v2.page.Task.Initiator">Initiated By</UI-TERM>** filter is added to the task list. You can also search for tasks by **<UI-TERM key="ocp-v2.page.Result.Success.TaskName">Task Name</UI-TERM>**.
* The **<UI-TERM key="ocp-v2.Detail.Parameter.List.WhetherTheRestartTakesEffect">Restart to Apply Changes</UI-TERM>** column is added to the OCP system parameter management list.
* You can specify the installation directory of the Agent by using the `ocp.agent.home.path.prefix` parameter.
* You can change the TopN setting by using the `ocp.perf.workload.report.tenant-top-sql-limit` parameter.
* You can enable or disable the automatic snapshot feature by using the `ocp.perf.snapshot.generation.enable` parameter. You can also generate snapshots for specified clusters by using the `ocp.perf.snapshot.generation.white-list` parameter.

## Fixed issues

OCP V4.0.1 fixes the following issues:

1. Fixed the issue where the tenant allowlist synchronization fails when OCP is upgraded from an earlier version to V3.3.3 in some scenarios.

2. Fixed the issue where the units of the io_util and io_qusize metrics in OCP alerts are incorrect.

3. Fixed the issue where OCP still uses the original RS to execute the upgrade script after the RS changes in some scenarios.

4. Fixed the issue where the manual refresh and automatic refresh of the replica view in the cluster resource management use different interfaces.

5. Fixed the issue where a server error “Error writing JSON output” is reported when the Trace details of a SlowSQL query are bound to a schema index.

6. Fixed the issue where the proxyro@sys password of the Meta cluster stored in the password vault is incorrect when OCP is deployed by using Antman.

7. Fixed the issue where the installation template cannot find the `sysctl` command because the PATH directory inherited by the agent started by using ssh is too small.

8. Fixed the issue where an OBProxy cluster is permanently locked and cannot be maintained in some scenarios.

9. Fixed the issue where the upgrade path cannot be found when OCP uploads the debuginfo package of the target version.

## Limitations

### Hardware requirements

OCP-Server can be installed on a physical server or in a Docker container. OCP-Server supports multi-node high availability deployment.

The following table lists the minimum hardware requirements for OCP-Server nodes.

| Hardware  | Requirement                                 |
|-----|------------------------------------|
| CPU | <li>X86_64, 8 cores</li><li>ARM aarch 64 architecture, 8 cores</li> |
| Memory  | 16 GB of available memory                         |
| NIC  | 10 GbE NIC                               |

OCP-Agent consumes very few resources and has no special requirements for the hardware resources of the installation node.

### Operating system requirements

The following table lists the operating system requirements for installing OCP-Server (including OCP-Agent).

| Server type       | Operating system       | Supported versions      |
|-------------|------------|-----------|
| x86_64      | RHEL       | 7.2 and later |
| x86_64      | CentOS     | 7.2 and later |
| x86_64      | AliOS      | 7.2 and later |
| x86_64      | openSUSE   | 12SP3 and later |
| ARM aarch64 | AliOS      | 7.2 and later |

| x86_64 | Debian       |   Debian GNU/Linux 11 (bullseye)    |
