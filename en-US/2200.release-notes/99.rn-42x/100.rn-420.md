## V4.2.0 BP1

OCP V4.2.0 BP1 supports seven scenarios for automatic recovery, including automatic recovery of OBServer and arbitration services, tenant and OBProxy expansion, and SQL-level throttling, based on alert rules. It provides actionable emergency response solutions based on alert rules and offers quick access to emergency response scenarios on mobile devices, thereby improving the stability of OceanBase Database services.

### Version information

* **Version:** V4.2.0 BP1

* **Previous version:** V4.2.0

* **Version release date:** September 22, 2023

### New features

* Provides actionable emergency response solutions based on alert rules. The main features include:

  * Resolves specific issues in seven scenarios based on specific types of alerts:

    * In the scenario where an OBServer or arbitration service crashes, OCP automatically restarts the OBServer and arbitration service (only once within 12 hours).

    * In the scenario where the `ob_tenant_request_queue_over_threshold` alert is triggered, OCP automatically expands the CPU resources of the tenant by 120%.

    * In the scenario where the `tenant_memstore_percent_over_threshold` alert is triggered, OCP automatically expands the memory resources of the tenant by 120%.

    * In the scenario where the client connection ratio of OBProxy exceeds the threshold, OCP automatically expands the client connections (client_max_connections) and memory (proxy_mem_limited) of the cluster by 120%.

    * In the scenario where an SQL execution plan is abnormal, SQL performance decreases, or CPU usage spikes, OCP provides emergency solutions such as refreshing the plan cache, binding execution plans, and SQL-level throttling.

  * Supports pushing alert information and solutions to external tools such as "Lark", "DingTalk", and "WeCom", allowing users to quickly handle emergencies through their mobile devices.

  * Supports marking alerts with emergency response scenarios for quick query.

  * Supports recording and querying Open API calls for subsequent tracing.

  * Supports setting up alert features at the cluster, tenant, and OBServer levels.

* Adds tenant queue backlog alert capabilities to help users promptly identify and resolve tenant performance issues.

* Adds disk unavailable alerts to help users quickly detect hardware failures and avoid impacting normal business operations.

* If the arbitration service is enabled at the cluster level and the sys tenant replica meets the 2F/4F requirements, the arbitration service is automatically enabled.

### Key features

#### Tenant-level IOPS isolation

OceanBase Database V4.0 virtualizes disk bandwidth (IOPS) to address I/O contention between tenants, enabling it to behave as if each tenant runs on separate physical disks. This achieves the strongest resource isolation capabilities. You can specify the maximum IOPS when creating a unit specification. All business requests under the corresponding user are then limited by this IOPS, achieving I/O isolation between tenants.

#### Physical standby database functionality at the tenant level

Before OceanBase Database V4.1.0, a cluster has two roles: a primary cluster and a standby cluster. The standby cluster is a backup of the primary cluster, ensuring transaction consistency. The primary cluster automatically transmits redo logs to the standby cluster. The standby cluster automatically applies these redo logs. The data and schema are physically consistent across the primary and standby clusters. OceanBase Database V4.1.0 introduces tenant-level primary/standby architecture. In this architecture, each cluster is a container for tenants. A tenant has a primary/standby relationship with other tenants. This relationship is determined by whether the tenant provides disaster recovery or read-only services. The primary tenant provides complete database services, including queries, DML, and DDL. The standby tenant provides only disaster recovery and read-only services. Tenant-level primary/standby architecture ensures high availability of a tenant.

You can use log-based or network-based technologies to set up a physical standby database:

1. Physical standby database based on log archiving

   In a physical standby database based on archive logs, the redo logs of the standby tenant are sourced from archive logs of the primary tenant or other standby tenants. This is similar to the Far Sync feature in Oracle databases. The standby tenant interacts only with the archive logs, without any other form of interaction with the primary or other standby tenants. In this deployment mode, the standby tenant does not require a network connection to the upstream tenants. However, its synchronization performance and availability depend on the medium used for the archive logs.

2. Physical standby database with network-based architecture

    In a physical standby database that is connected to the primary database over the network, the standby tenant can read logs from the primary tenant or other standby tenants directly over the network. This is similar to replication in a MySQL database. In this deployment mode, the standby tenant can communicate with the primary tenant and other standby tenants. The standby tenant sends RPC requests over the network to read redo logs from the primary tenant cluster. Additionally, for high availability of the standby tenant during primary tenant node failures or log recycling, the standby tenant needs read-only access to system views in the primary tenant. In this deployment mode, the standby tenant can read online logs or archived logs (if the primary tenant has enabled archive mode) from the primary tenant cluster. These sources of logs are automatically switched, and the change is transparent to both the standby tenant and the business users.

The tenant roles of an OceanBase cluster are divided into two types: the primary tenant (PRIMARY) and the standby tenant.
(STANDBY). You can change the role of a tenant through routine switchover between the primary and standby tenants or disaster recovery switchover between the primary and standby tenants.

  1. Role swaps between primary and standby databases. You can swap roles between the primary tenant and one of the standby tenants to ensure data loss does not occur.
  2. Primary and standby database disaster recovery switching: If the primary database is unavailable, you can switch a standby database to the primary one.

The product is available only in OceanBase V4.2.0 and later versions.

#### Resource isolation within the tenant

In OceanBase Database, DBMS_RESOURCE_MANAGER is the system package in PL that you can use to manage the allocation of resources in the database. The configuration is complex. OCP reduces the configuration difficulty by offering highly refined management features. OCP supports resource isolation at the user level and at the SQL statement level.

1. Simplifies the process of creating a resource isolation plan: configure the isolation plan > configure the resource group > apply the isolation restrictions.

2. Optimize the semantics of resource isolation for users, such as CPU, IOPS, upper and lower limits, and weights.

3. Support dynamic adjustments of resource isolation plans, including enabling, disabling, modifying, and deleting them.
