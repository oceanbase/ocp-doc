## V4.2.1

OCP V4.2.1 officially supports OceanBase Database V4.2.1. It also supports monitoring and alerting for all components of OceanBase Database. This includes user-defined monitoring, enhanced tenant and session-level end-to-end tracing, and additional monitoring and alerting capabilities for OBLB and OBDNS. In addition, this version includes 17 optimizations in areas such as cluster management, tenant management, monitoring and alerting, and task management. These optimizations aim to improve the usability of the product and create a more user-friendly database management platform.

### New features

#### OceanBase V4.x support

* You can enable full-link diagnostics at the tenant and session levels. This feature allows you to analyze transaction-level time consumption across three levels: client > OBProxy > OceanBase cluster. This helps you quickly locate the root cause of issues and resolve them promptly. To use this feature, you must deploy the OpenSearch service, and the component versions along the entire chain must meet specific requirements. For more information, see [Query a trace](../../1300.log-service/400.trace-query.md).

* The `__all_virtual_dump_tenant_info` view is adapted to monitor and alert on tenant queue usage.

* The tenant=all configuration item is adapted. This configuration item only takes effect for regular tenants and does not take effect for sys and meta tenants.

* The RS job view is adapted. New task types, such as `ALTER_TENANT_PRIMARY_ZONE`, `ALTER_TENANT_LOCALITY`, and `ALTER_RESOURCE_TENANT_UNIT_NUM`, are added.

* You can view the usage of the OceanBase log disk.

#### Feature enhancements

* **OBProxy management**

  * You can hot-restart OBProxy V3.2.8 and later. This helps avoid service interruptions during maintenance or upgrades.

  * You can enable, restart, stop, and batch start, restart (including hot restart), and stop OBProxy nodes in an OBProxy cluster. This enhances OBProxy management capabilities and improves user efficiency.

* **Monitoring and alerts**

  * You can customize monitoring capabilities by defining collection items and monitoring items. You can associate monitoring items with monitoring charts and alerts to implement customized monitoring and alerting. This addresses scenarios where built-in OCP alerts do not meet customer business requirements (only applicable to sys tenant metrics).

  * You can enable alerts for OBLB and OBDNS, covering 16 metrics such as process status and process connectivity. This provides comprehensive alerting capabilities for the entire OceanBase architecture.

  * You can monitor the percentage of active Memstore. The path is **<UI-TERM key="ocp-v2.Cluster.Arbitration.Tenant">Tenant</UI-TERM>** > **<UI-TERM key="ocp-v2.Detail.Realtime.PerformanceMonitoring">Performance Monitoring</UI-TERM>** > **Performance and SQL** > **MEMStore Usage Percentage**.

  * You can monitor the number of tenant dumps. This helps prevent cluster-level major compactions triggered by exceeding the dump threshold for a single tenant in OceanBase V3.X, thereby minimizing business impact.

  * You can receive alerts when the total space occupied by the OceanBase recycle bin exceeds 100 GiB. This helps mitigate the impact of excessive partitions and delayed cleanup in the recycle bin on customer business.

  * You can receive alerts when the OCP agent version is inconsistent with the OCP version. This prevents abnormal behavior during subsequent maintenance and improves system stability.

* **<UI-TERM key="ocp-v2.src.constant.auth.Inspection">Inspection</UI-TERM>**

  * You can detect connectivity between servers, including SQL and RPC ports. This helps quickly identify business interruptions caused by network or host failures.

  * You can check the usage of OceanBase macroblocks. This helps identify the actual data volume and disk usage of tenants and tables, enabling you to reduce disk fragmentation through major compactions.

### Feature optimizations

* When a cluster, tenant, OBProxy, or host is unavailable or offline, the system provides analysis of the root cause, error messages, error reasons, and solutions. This helps users resolve issues and ensure business stability.

* Cluster management:

  * When adding or replacing an OBServer, you can specify startup parameters such as `memory_limit` and `system_memory`. This solves issues such as failed expansion and resource waste when hardware resources are inconsistent within the cluster.

  * When creating an arbitration service, you can specify startup parameters such as `cpu_count` and `devname`.

  * When restarting a cluster, stopping a cluster, restarting a zone, stopping a zone, restarting an OBServer, or stopping an OBServer process, you can choose to perform a Memstore dump. This addresses the issue of slow OBServer recovery without a dump.

  * You can verify the paths and sizes of the cluster's log and data disks. This includes checking the log disk size and whether the data and log disks are deployed on the same physical disk. This helps prevent database runtime issues and improves system stability.

  * Deadlock detection now includes a warning: It is not recommended to enable this feature in production systems of OceanBase V3.X.

  * You can detect whether the Large System Extensions (LSE) extensions supported by the CPU are lower than ARM8.1. This helps prevent OceanBase cluster deployment failures.

* Host management:

  * You can associate a host's IP address with its corresponding OceanBase cluster or OBProxy cluster and quickly jump to the cluster.

  * You can quickly jump to the corresponding task for a host in maintenance mode (such as host deletion or OCP agent reinstallation).

* Monitoring and alerts management:

  * Active alerts, historical alerts, and status bars now include reminders for active alerts. This increases user attention to current active alerts.

  * **<UI-TERM key="ocp-v2.page.Information.Alert">Alerts</UI-TERM>** > **<UI-TERM key="ocp-v2.page.Alarm.AlarmEvent">Alert Events</UI-TERM>** now include an alert classification option. This helps users quickly identify alert types and improves product usability.

  * In alert information (such as cluster, tenant, and OBServer alerts), affected host IPs or tenant names are provided. This helps users quickly identify the scope of impact.

  * Cluster names are now displayed as `Cluster Name: Cluster ID`, and primary/standby cluster markers are added.

* Backup and restore management:

  Cluster names are now displayed as `Cluster Name: Cluster ID`, and primary/standby cluster markers are added.

* Log service management:

  In **<UI-TERM key="ocp-v2.Log.Trace.LinkQuery">Trace Query</UI-TERM>** > **<UI-TERM key="ocp-v2.Log.Trace.SearchContent">Search</UI-TERM>**, new conditions such as `sql_trace_id`, `trans_id`, `sess_id`, and `client_info` are added. This helps associate user links and improves query efficiency.

* Task management:

  * Failed tasks now display error messages and locate the first error log. This helps users efficiently identify the root cause of issues.

  * Failed tasks can be retried in batches, such as restarting or reinstalling the OCP agent. This significantly improves user maintenance efficiency.

  * Clusters, tenants, OBProxies, and hosts in maintenance mode can be quickly associated with tasks. This helps users quickly view task statuses for subsequent maintenance operations.

### Key features

#### End-to-end diagnostics at the tenant and session levels

OceanBase Database is a distributed database. The call chain between the client and the database is extremely complex. When a business application experiences timeouts or performance anomalies, users often cannot determine whether the issue is within OceanBase Database or related to the network. They can only analyze the issue based on experience and OBServer logs, which can lead to longer analysis and resolution times, affecting business stability. Therefore, OCP provides an end-to-end diagnostic mechanism to monitor the entire chain from the client to the OBProxy to the OBServer, helping users quickly identify the root cause of the issue.

To view related logs in OCP, you must first configure the data middleware module, link query collection, and OpenSearch (ES) parameters. If you only need to enable this feature for specific tenants or sessions, disable it for other tenants and go to **<UI-TERM key="ocp-v2.src.hook.useMenu.LogService">Log Service</UI-TERM>** > **<UI-TERM key="ocp-v2.Log.Trace.LinkQuery">Trace Query</UI-TERM>**. You can filter logs by time, tenant, search content (such as `sql_id`, `trans_id`, and `sess_id`), and link duration. The current end-to-end diagnostics track transactions in the database and statistics include link duration, driver duration, OBProxy duration, and OB duration. By analyzing these durations, you can identify the main issue and view specific durations (Span/Tag) in the corresponding trace to quickly find the root cause.

#### Custom monitoring

Custom monitoring allows you to customize monitoring charts and alerts based on your business scenarios when the built-in monitoring features in OCP do not meet your needs. This helps you promptly detect changes in the system and make timely and informed decisions.
The feature module consists of three tabs: data collection items, metrics, and charts. Specifically:

1. Data collection items represent the original monitoring data collected from different data sources. The system currently provides more than 50 data collection items.

2. Metrics represent calculated indicators based on data collection items, such as maximum, minimum, or average values. You can select or customize expressions based on your monitoring data usage. The system currently provides more than 200 metrics.

3. Charts can consist of one or more metrics. You can choose the chart placement and preview the chart. Additionally, you can set custom alerts based on the metrics to monitor the corresponding indicators.
