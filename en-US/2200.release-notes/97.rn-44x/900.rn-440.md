### Key features

#### Real-time monitoring

To address the complexity of end-to-end performance monitoring and fault localization in a distributed database environment, OCP introduces an end-to-end real-time monitoring solution. This solution establishes a five-tier monitoring system covering OBProxy > OceanBase cluster > tenant > host > unit. The three core capabilities of this solution enhance the O&M experience:

* **3D topology visualization for a comprehensive view of the architecture**: A dynamic 3D visualization engine is used to present the logical relationships and physical deployments between OBProxy and clusters, clusters and hosts, tenants and OBServer nodes. This solution supports topology drilling down from the global architecture to individual units, providing an intuitive view of resource distribution and dependencies, making the "black box" operation state of distributed systems transparent.

* **Comprehensive metric monitoring for quick fault localization**: Real-time monitoring aggregates over 10 core performance metrics, including QPS, TPS, RT, connection count, and CPU/memory usage. By analyzing performance trends, it accurately identifies performance turning points. Users can directly view associated alerts on the topology diagram and jump to the alert center, enabling one-click tracing from metric anomalies to the root cause of faults, significantly improving fault localization efficiency.

* **Dual-mode data presentation for diverse O&M scenarios**: Structured table data views are provided, complementing graphical and digital information. This approach meets the needs of managers for a global overview while providing deep analysis data for technical staff, effectively reducing the cognitive and management barriers of distributed systems.

With the end-to-end real-time monitoring solution, users can better manage and optimize system performance in daily O&M, fault troubleshooting, and large-screen displays, enhancing system stability and reliability.

#### KMS TDE encryption

The TDE feature in OceanBase Database is a powerful data protection measure designed to ensure the security of data stored on disks. Through an invisible encryption mechanism, TDE automatically encrypts data as it is written to storage devices and automatically decrypts data when it is read. This process is transparent to users, effectively preventing hackers and malicious users from accessing sensitive data in data files, database backups, or disks.

OceanBase Database's TDE feature uses a two-tier key system for encryption and decryption. The smallest encryption granularity is a table in a database, but the table must be located in an encrypted tablespace. A tablespace can be understood as a collection of tables, a concept introduced by OceanBase Database to ensure compatibility with Oracle Database. Each encrypted tablespace is associated with a specific encryption algorithm and a corresponding data key, used to encrypt data within that tablespace. Additionally, each tenant has a master key, which is used to encrypt the data keys of the tablespaces. To prevent unauthorized decryption, the master key is typically stored in a dedicated Keystore.

KMS supports a series of key management functions, including key generation, storage, backup, recovery, and destruction. Through KMS, users can conveniently manage access permissions to their digital assets, ensuring that only authorized users can access specific data resources. Moreover, KMS helps users avoid the security risks associated with lost or forgotten keys.

To standardize key management, OCP acts as a proxy for the KMS service, providing unified key management services and interfaces. This approach shields OceanBase Database from the differences among KMS services of various cloud vendors. Users only need to provide the access domain name, AccessKey (AK), SecretKey (SK), and master key ID of Alibaba Cloud or Tencent Cloud to easily enable the KMS TDE encryption feature for tenants.

### New features

#### Basic Maintenance

1. **Cluster Management**: During cluster upgrades, automatic prompts are provided if dynamic partitioning is enabled to avoid disruptions or business impact from disallowing DDL operations. Supported OceanBase versions are [V4.2.5 BP2, +∞).
2. **Cluster management**: During the installation, deployment, or upgrade of OceanBase Database, if a host does not support the AVX instruction set, the operation will be stopped automatically to prevent potential compatibility issues. Supported OceanBase Database versions: [V4.2.5, V4.2.5 BP2), [V4.3.5, V4.3.5 BP4).
3. **Cluster Management**: Supports the display of primary/standby information at the tenant level, major compaction, and data backup information, enabling users to quickly understand the current status of the cluster.
4. **Tenant Management**: When you create a MySQL tenant, you can set the `ob_compatibility_control` variable. The OceanBase Database versions for this feature vary with the value of `ob_compatibility_control`. Supported OceanBase Database versions are [V4.2.3, V4.3.0) and [V4.3.2, V4.3.5 BP3).
5. **Tenant Management**: You can define custom tenant connection strings to enable users to access databases by using different domains.
6. **Tenant management**: The Create routine privilege is supported for granting a user in a MySQL tenant. This feature is supported in OceanBase Database versions [V4.2.2, V4.3.0) and [V4.3.1, +∞).

#### Monitoring alerts

1. Support OceanBase V2.x and V3.x master/standby cluster synchronization status (SYNCHRONIZATION_STATUS) alerts.
2. Added eight tenant-level monitoring metrics: MemStore read lock request success rate, MemStore write lock request success rate, RPC request success rate, GTS request count, transaction rollback ratio, fuse row cache hit rate, schema cache hit rate, and temporary page cache hit rate.
3. Added two cluster-level monitoring metrics: average RPC network latency and average number of failed RPC deliveries over the sampling interval.
4. The monitoring metrics in a specific time period, including the maximum values, average values, and current values, are supported in the OBProxy cluster.

#### Disaster recovery management

1. A primary tenant can be backed up by multiple secondary tenants, and cascading disaster recovery is supported. This feature allows a primary tenant to seamlessly switch the synchronization source among its secondary tenants, facilitating remote switching rehearsals.
2. In standby synchronization mode based on archived logs, you can set the restore time point of a standby tenant by using the `ocp.standby.tenant.restore.advance.seconds` parameter. The default value is current time minus 60 seconds.
3. The overview page supports displaying the primary and standby relationships between tenants.

#### Scenario Management

1. In active-standby deployment, if two tenants are configured for active-standby, and the two tenants are assigned the same service name, data traffic is automatically switched from the standby tenant to the primary tenant when an error occurs in the standby tenant.
2. After the binlog process (OBM) crashes, ODP automatically restarts the binlog process within 30 minutes, and this process is only effective for 30 minutes.

#### Binlog management

When you create a Binlog instance, you can set a Clog parsing start point by using a binlog offset. The downstream systems can then subscribe to data at the required start point.

#### Restore a Backup

1. You can enable or disable the dynamic partition feature based on the actual business situation during full restoration to avoid partition data loss caused by this feature. Supported OceanBase Database versions: [V4.3.5 BP2, +∞).
2. Tenants that are restored can be read-only and cannot be majorated or backed up. Supported OceanBase versions are [V4.3.3, +∞).
3. The backup task skips the locked tenants by default.
4. Support advanced options for S3-compatible object storage types.
   * When you set delete_mode to delete (the default) or tagging, it takes effect only in OceanBase Database V4.2.3.0 to V4.2.5.0, and OceanBase Database V4.3.0 and later.
   * checksum_type=md5 (default) /crc32. It is supported in [V4.2.1.6, V4.2.2.0) and [V4.2.3.0, +∞).
   * addressing_model=virtual_hosted_style（default）/path_style, which is supported in OceanBase Database V4.2.1.9, V4.2.2.0, V4.2.5.1, V4.3.0.0, V4.3.5.0, and later.

### Product optimization

#### Cluster Management

1. The Overview tab is provided to display the remaining CPU, memory, and data storage resources. This feature allows you to monitor resource usage and improve the O&M efficiency.
2. When the zone contains only one OBServer node with replicas, the OBServer node cannot be reinstalled.

#### Tenant Management

Tenant specification queries support searching for tenant specifications by Unit specification name, addressing query inefficiency caused by excessive number of tenant specifications.

#### Managing Hosts

The host list provides the View Standardization Report function in the Actions column.

#### Backup restoration

1. The sys tenant, which is the system management tenant, does not support backup and restore operations. The backup and restore page for the sys tenant has been removed to avoid confusion and incorrect operations by users. This change applies to OceanBase Database of version V4.0 or later.
2. During tenant recovery, the user can choose between the following options: view the task progress in the Task Center, or continue the operation on the Recovery Start page.

#### Others

1. **AI Assistant** provides general conversation capability and implements the document search capability in the business scenarios where no large model is configured.
2. Remove the character limit for the tag display in the details view of clusters, tenants, OBProxy, and hosts.
3. **Operational audit** supports displaying the IP address of the client that accessed the database.

### Product behavior change

1. Due to the behavior changes of Tencent Cloud COS, it is recommended that you use the S3 protocol as the COS protocol. OceanBase Database V4.2.1.9 to V4.2.2, V4.2.5.0 to V4.3.0, and V4.3.3.0 to V4.4.0 support the S3 protocol. OceanBase Database V4.4.0 and later no longer support the COS protocol.
2. Removed the exclusive-host limitation for the binlog service and enabled it to coexist with other services on the same host (recommended only for test environments), effectively reducing deployment and maintenance costs.

### Hardware requirements

OCP-Server can be installed on a physical server or in a Docker container. OCP-Server supports multi-node high availability deployment.

The following table describes the minimum hardware requirements for OCP-Server nodes.

| Hardware | Requirement                 |
|-------|------------------------------------|
| CPU  | <li>X86_64, 8 cores</li><li>ARM aarch 64 architecture, 8 cores</li> |
| Memory | 16 GiB available memory             |
| NIC | 10 GbE NIC                |

OCP-Agent consumes very little resources and has no special requirements for the hardware resources of the installation node.
