# Overview of Binlog service

The Binlog service is a service that collects transaction logs of OceanBase Database and converts them into MySQL Binlogs. It is mainly used in scenarios such as real-time data subscription. OCP supports GUI-based single-node deployment or cluster deployment of the Binlog service, and allows you to perform basic O&M operations on Binlog clusters and instances. OCP also supports monitoring and alerting for the Binlog service, providing resource usage views of Binlog clusters and allowing you to associate the views with alerts to help you quickly locate and resolve issues.

## Background information

In MySQL, binlogs serve as the starting point for data subscription. Users can enable binlogs with relatively low performance and resource consumption to support various downstream business scenarios.

OceanBase Binlog Service is a feature introduced to ensure compatibility with MySQL binlogs. It allows customers to reuse their existing MySQL binlog incremental parsing systems to synchronize incremental data from OceanBase Database's MySQL mode, without requiring secondary development or setting up a new environment. Binlog Service aligns with MySQL Binlog V4 protocol, offering the same features (such as multiple subscription connections) and ensuring the uniqueness of data in binlogs. You can seamlessly use your existing MySQL-based incremental data subscription solutions and switch them to OceanBase.

## Architecture overview

**<UI-TERM key="ocp-v2.Component.BinlogService.BinlogCluster">Binlog Cluster</UI-TERM>**

A Binlog Cluster is a unified service composed of one or more Binlog Servers. When multiple Binlog Servers exist within the cluster, the tenant Binlog service starts by selecting an appropriate Binlog Server based on load balancing logic. If any Binlog Server fails, another normal Binlog Server takes over its Binlog service.

**Binlog Server**

Binlog Server manages several Binlog instances on the node and processes SQL requests. Multiple Binlog Servers share information through MetaDB. Binlog Server supports custom SQL API for managing Binlog instances.

**Binlog Instance**

A Binlog instance is a tenant-level Binlog instance responsible for generating and sending binlogs, and for handling TCP monitoring based on the MySQL protocol to process SQL requests. An OceanBase Binlog instance can be likened to a MySQL instance. Multiple OceanBase Binlog instances within the same tenant can be compared to MySQL primary and standby instances. They support MySQL binlog-related SQL, protocols, and variables, such as `SHOW MASTER STATUS`.

## Features of Binlog Service

The binlog protocol of OceanBase Database's MySQL mode is largely consistent with that of MySQL Binlog V4, so its basic features are similar to those of the MySQL Binlog protocol. The specific features are described as follows:

* Supports generating only Row-based Replication (RBR) formatted binlogs.
* Generates binlogs based on OceanBase Database's tenant level.
* Supports only specific binlog events related to changes, such as Format_desc, Previous_gtids, Rotate, Gtid, Query, Table_map, Write_rows, Update_rows, and Delete_rows.
* Supports GTID mode.
* Supports resumption of binlog event transmission without duplication or loss.
* Supports converting incremental DDL operations in OceanBase Database into native MySQL syntax.

## Limitations

### Performance limitations

The performance of the Binlog conversion service is constrained by resource configuration and the parsing capability of Clogs. Different Binlog versions support varying maximum Clog parsing performance and maximum RPS, as detailed in the **Limitations** section of [Introduction to Binlog Service](https://www.oceanbase.com/docs/common-oblogproxy-doc-1000000003053703). If the traffic of the source business exceeds these limits, the latency of the Binlog conversion service may increase.

When the business pressure is controllable, the latency of the Binlog conversion service is usually maintained within 1 second. However, in special circumstances, such as frequent data definition language (DDL) operations or large transactions in the database, it cannot guarantee absolute second-level conversion latency.

### Version requirements

To access the Binlog Service, the following versions and tenant modes must be met:

* OceanBase Database V3.x must be V3.2.4.4 or later. V4.x must be V4.1.0.1 or later.
* OBProxy must be V4.2.1 or later.
* Binlog Service must be V4.0.0 or later.
* MetaDB must be 2.2.77 or later (Built Feb 14 2022 18:11:59).
* Only MySQL mode is supported.

### SQL compatibility

Due to the differences between the DDL syntax of OceanBase Database in MySQL mode and MySQL DDL syntax, which includes some unique extended syntaxes in OceanBase Database in MySQL mode, some of these DDL syntaxes may not be parseable.

### Data types

Due to differences in precision and implementation between OceanBase Database in MySQL mode and MySQL, not all data types are fully compatible. Incompatibilities are described as follows:

* OceanBase Database in MySQL mode does not support extended semantics for the ENUM and SET data types. For example, the SET data type does not support more than 64 values, duplicates, or the ENUM data type does not support inserting undefined data (such as an empty string).

* VARCHAR(n > 65535) is not supported.

* LONGBLOB and LONGTEXT are supported for a maximum of 48 MiB.

* MEDIUMBLOB, LONGBLOB, BLOB, MEDIUMTEXT, LONGTEXT, TEXT, JSON, and GIS data types are stored using LOB types in the underlying database. By default, values greater than 4 KiB are stored off-row, which may be incompatible with MySQL:

  * If data is stored off-row, it is stored in-row after an UPDATE operation. The before-image output is NULL, and the after-image output is the updated data.
  * For tables with LOB columns stored off-row, updates to non-LOB columns result in NULL outputs for both the before-image and after-image.
  * For LOB columns stored off-row, the before-image output is NULL after a DELETE operation.

    <main id="notice" type='explain'>
    <h4>Note</h4>
    <p>LOB columns smaller than 4 KiB are treated like regular columns, with actual column data recorded in the primary table. LOB columns greater than 4 KiB are stored in a LOB auxiliary table, with the primary table recording the auxiliary table information for the LOB column. 4 KiB is the default size.</p>
    </main>

* Virtual generated columns are not supported in OceanBase Database V4.x and later.

* CTAS is not supported.

    In CTAS scenarios, OceanBase Database V4.x cannot output accurate table names, such as `create table t2 as select * from t1`, which involves creating the `t2` table and writing the `t1` data to the `t2` table. OceanBase Database V4.x can only output `__ctas_xxxx` as a temporary table name instead of `t2`.

## Current status of downstream ecosystem integration

### Synchronization of existing data

The Binlog Service only provides incremental data synchronization. However, when synchronizing data from OceanBase Database in MySQL mode to downstream systems, existing data synchronization may also be involved. The following describes some common considerations during the synchronization of existing data:

* Only incremental snapshot reads are supported.
* Table-level snapshots and the FLUSH TABLES WITH READ LOCK command are not supported.
* The MySQL interactive_timeout and warning_count timeout parameters can be set.
* The heart.interval heartbeat timeout parameter can be set.
* Existing data can be pulled in parallel, if the MySQL synchronization component supports this feature.

### Tools for downstream ecosystem integration

Mainstream MySQL binlog parsing tools such as flinkcdc, Canal, and MaxWell can be integrated with the Binlog Service.

## Use Binlog service in OCP

### Environment preparation

1. The Binlog service depends on jq, mysql, java, and diff. You need to manually install these on the host. Here is an example of installation, so you need to adapt it to your environment:

    ```bash
    # 1. jq
    sudo yum install jq

    # 2. mysql
    sudo yum install mysql

    # 3. java
    # If you already have a Java environment, you can directly configure the environment variables.
    sudo yum install java-1.8.0-openjdk*
    echo "export JAVA_HOME=/usr/lib/jvm/java-1.8.0" >> /etc/profile
    echo "export JRE_HOME=${JAVA_HOME}/jre" >> /etc/profile
    echo "export CLASSPATH=${JAVA_HOME}/lib:${JRE_HOME}/lib:${CLASSPATH}" >> /etc/profile
    echo "export PATH=${JAVA_HOME}/bin:${JRE_HOME}/bin:${PATH}" >> /etc/profile

    # 4. diff
    sudo yum install diffutils
    ```

    Note that the `echo "export JAVA_HOME=/usr/lib/jvm/java-1.8.0" >> /etc/profile` line needs to use the actual directory of your Java environment. You can use the `ls /lib/jvm | grep java` or `which java` command to find out the path.

2. Check if the dependencies have been installed successfully:

    ```bash
    # 1. jq
    command -v jq

    # 2. mysql
    command -v mysql

    # 3. java
    echo $JAVA_HOME

    # 4. diff
    command -v diff
    ```

### Quick start

You can follow the steps below to use the Binlog service in OCP:

1. Create an OceanBase cluster, OceanBase tenant, and OBProxy cluster that meet the requirements specified in **Limitations** > **Version requirements**.

    For more information, see [Create a cluster](../600.cluster-functions/200.create-a-cluster/100.create-a-distributed-cluster.md), [Create a tenant](../700.tenant-functions/300.create-a-tenant.md), and [Create an OBProxy cluster](../800.obproxy-functions/200.create-an-obproxy-cluster.md).

2. The Binlog service is provided as a separate component. You can obtain the component by creating a Binlog cluster.

    For more information, see [Create a Binlog cluster](200.create-a-binlog-cluster.md).

3. Enable the Binlog service for the OceanBase tenant to collect transaction logs from OceanBase and convert them into MySQL Binlogs.

    For more information, see [Manage Binlog service of a tenant](../700.tenant-functions/600.manage-a-tenant/700.manage-binlog-service-of-a-tenant.md).
