# Manage service names

This topic describes the background information, version restrictions, and usage scenarios and methods of service names.

## Background

OCP V4.2.0 supports tenant-level primary-standby configuration. However, due to the limitations of OBProxy and OceanBase, after users perform routine primary-standby tenant switching or disaster recovery switching on OCP, they must modify the database connection string of their applications. In this case, the automatic routing capability after primary-standby cluster switching cannot be achieved. To address this, OceanBase has designed a solution that supports automatic routing. This solution requires collaboration among OCP, OBProxy, and OceanBase.

In OceanBase, the SERVICE_NAME (i.e., service name) defines a service. Through SQL commands, the service name can be assigned to a specific tenant. OCP ensures that the service names of primary and standby tenants are the same, while non-primary/standby tenants have different service names. The following table lists the primary and standby tenants.

| Tenant Name | Role | OceanBase Cluster | Service Name |
| --------- | ---------- | --------- | -------- |
| TenantA | PRIMARY | ClusterA | ServiceTest |
| TenantB | STANDBY | ClusterB | ServiceTest |

The following figure shows how a business application accesses a tenant by using the service name:

![1](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/ocp/433/202411141354.png)

OceanBase provides four operations for creating, starting, stopping, and deleting a service name for a tenant, corresponding to four SQL statements. After a service name is created, it is automatically started. Only after the service name of a tenant is successfully started can a session be established through the service name. To delete a service name, it must be stopped first.

<main id="notice" type='notice'>
<h4>Notice</h4>
<p>OceanBase does not enforce the restriction that a service name must be assigned to a primary-standby tenant pair. In other words, OceanBase allows a service name to be assigned to any tenant, while OCP imposes this restriction. </p>
</main>

## Version requirements

OCP, OceanBase, and OBProxy must meet the following version requirements:

* OCP: [V4.3.1, +∞).
* OceanBase: [4.2.1.9, 4.2.2.0), [V4.2.4.0, V4.3.0.0), and [V4.3.3.0, +∞).
* OBProxy: [V4.3.1.0, +∞).

## Prerequisites

The user logged in to OCP must have the following permissions:

* **Cluster Maintenance** or **Tenant Maintenance** resource permissions.
* Permissions to access the **<UI-TERM key="ocp-v2.page.Overview.Overview">Overview</UI-TERM>** menu of the tenant.

## Function usage

### Automatic routing

To implement automatic routing, the following two conditions must be met:

1. The primary and standby tenants have the same service name.
2. The primary and standby tenants belong to OceanBase clusters that are associated with the same OBProxy cluster. The OBProxy cluster can automatically route traffic to the primary or standby tenant.

### Set a service name

After you set a service name for a tenant in OCP, you can connect to the tenant by using the service name.

```shell
obclient -hIP -PPORT -uroot@SERVICE:service1 -pPASSWORD
```

In the preceding statement, `SERVICE` is a keyword. You must replace `service1` with the actual service name. OCP provides three ways to set a service name for a tenant:

* **Specify a service name when you create a tenant**: You can directly specify a service name when you create a tenant.

    ![2](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/ocp/433/202411141356.png)

* **Set a service name on the tenant details page**: You can add a service name for a tenant on the tenant details page. You can also **<UI-TERM key="ocp-v2.Auth.User.Detail.Editing">Edit</UI-TERM>** or **<UI-TERM key="ocp-v2.MultiCluster.Detail.Delete">Delete</UI-TERM>** the service name.

    ![3](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/ocp/433/202411141357.png)

* **Synchronize the service name**: OCP synchronizes tenant information every minute. It compares the tenant information in OceanBase internal tables/views with the metadata in OCP and updates the information. During this process, the service name of the tenant is updated.

### Apply automatic routing in a switchover scenario

#### Routine switchover

The following two pre-checks are added to a routine switchover:

1. The primary and standby tenants do not have service names or have the same service name.
2. If the primary and standby tenants have service names, the service names cannot be the same as those of other tenants that are not in a primary/standby relationship.

Before a routine switchover, if the OceanBase cluster where the standby tenant is located is not associated with the OBProxy cluster associated with the OceanBase cluster where the primary tenant is located, OCP issues a warning: Automatic routing may not be available after the switchover. However, OCP does not prohibit the switchover. A routine switchover does not modify the service name of a tenant. You can use the `[username]@SERVICE_NAME:[serviceName]` format to access the OceanBase tenant through OBProxy without changing the connection string.

#### Disaster recovery switchover

When OceanBase performs a disaster recovery switchover, it deletes the service name of the new primary tenant. Therefore, you cannot connect to the new primary tenant by using the service name. To avoid changing the connection string, OCP wraps the feature. The following figure shows the scenario:

![4](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/ocp/433/serviceA.png)

After a disaster recovery switchover is performed on Tenant B, the original primary/standby relationship is divided into two parts: (Tenant B and Tenant C) and (Tenant A, Tenant D, and Tenant E). The service names of Tenant A, Tenant C, Tenant D, and Tenant E remain ServiceA. The service name of Tenant B is deleted. To avoid changing the connection string, OCP sets the service name of Tenant B to ServiceA and sets the service names of Tenant A, Tenant D, and Tenant E to **INVALID** at the end of the disaster recovery switchover. The **INVALID** status is a concept of OCP. It shields the service name of the tenant from OBProxy to prevent it from accessing the original primary tenant. Config Server only returns the service names of tenants whose status is not **INVALID**. The following figure shows how the **INVALID** status is displayed in OCP.

![1](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/ocp/433/01101645.png)

Before you perform a disaster recovery switchover in OCP, you can choose whether to set a service name for the new primary tenant. This is an optional operation. If the service name of the new primary tenant is the same as that of the original primary tenant, when OBProxy automatically accesses the new primary tenant, data inconsistency may occur because the new primary tenant has <code>RPO!=0</code>.

![1](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/ocp/433/01101646.png)

#### Decouple the primary and standby tenants

For OceanBase, decoupling the primary and standby tenants and performing a failover of the standby tenant are the same instruction. However, in OCP, they are two different features. The following figure shows the primary/standby relationship. At this time, the original primary tenant is in the normal state. After decoupling, OceanBase automatically deletes the service name of Tenant B. OCP also deletes the service name of Tenant C to prevent tenants that are not in a primary/standby relationship from having the same service name.

![5](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/ocp/433/serviceB.png)

### Multi-cluster mode

When the primary and standby OceanBase clusters are deployed in the primary and standby OCP clusters, respectively, both OCP clusters can return the RS list of the primary and standby OceanBase clusters. This way, you do not need to change the application connection string when the primary and standby OceanBase clusters are switched over. The following figure shows the scenario:

![6](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/ocp/433/202411141358.png)

After an OBProxy cluster is associated with either the primary or standby OceanBase cluster, the OBProxy cluster can obtain the RS list of the primary and standby OceanBase clusters. This depends on the following two conditions:

1. The cluster names of the primary and standby OceanBase clusters are the same. Therefore, when an OBProxy requests the RS list, it can use the cluster name of the primary or standby OceanBase cluster.
2. The proxyro@sys passwords of the primary and standby OceanBase clusters are the same. Therefore, you can associate the OBProxy cluster with only one OceanBase cluster. The proxyro password can be used for both.

To support the same capabilities of the primary and standby OceanBase clusters in a multi-cluster mode, OCP V4.3.2 and later versions support the association between an OceanBase cluster and an OBProxy cluster across OCP clusters. The following three features are supported:

1. You can associate an OceanBase cluster with a remote OBProxy cluster. A drop-down list displays the remote OBProxy cluster.

    ![1](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/ocp/433/202411141504.png)

2. You can associate an OBProxy cluster with a remote OceanBase cluster. A drop-down list displays the remote OceanBase cluster.

    ![1](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/ocp/433/202411141506.png)

3. When you create an OceanBase cluster, you can associate it with a remote OBProxy cluster. A drop-down list displays the remote OBProxy cluster.

    ![1](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/ocp/433/202411141508.png)

After an OBProxy cluster is associated with a remote OceanBase cluster, you can access the tenants in the remote OceanBase cluster through the local OBProxy cluster.
