# Create a standby tenant

If you have a primary tenant or a standby tenant, you can create a standby tenant for the current tenant. OCP supports two scenarios: creating multiple standby tenants for a primary tenant (one-to-many) and creating standby tenants for standby tenants (cascading).

## Background information

Since OceanBase Database V4.1.0, physical standby databases are implemented at the tenant level. In this model, the primary or standby role is assigned to a tenant, which can be either a primary tenant or a standby tenant. The cluster no longer has a primary or standby role, but rather serves as a container for tenants. A primary tenant is a business tenant created by users, supporting full database capabilities such as queries, DML, and DDL operations. A standby tenant, on the other hand, only provides disaster recovery and read-only services. A primary tenant and several standby tenants together form a tenant-level physical standby database high-availability solution.

## Prerequisites

* Make sure that the user logged in to OCP has the following permissions:

  * **Cluster Maintenance** resource permission.
  * **<UI-TERM key="ocp-v2.src.util.menu.SummaryInvestingComZa">Overview</UI-TERM>** permission for the tenant.

* Only OceanBase Database V4.2 and later versions support tenant-level primary-standby configurations.

* The status of the cluster where the standby tenant resides must be Running.

* By default, only one tenant can be created in a standalone instance. To create a standby tenant in a standalone instance, you must purchase the corresponding feature license and then [import the license](../../600.cluster-functions/300.manage-a-cluster/1400.import-license.md).

* When creating a standby tenant with a version earlier than OceanBase Database V4.2.1.8, do not use a baseline backup data file that is more than 30 days old to restore the physical standby database. This may cause functional anomalies in the physical standby database and affect tenant merging.

* Before enabling arbitration service for a tenant, make sure that the following conditions are met:

  * The cluster where the tenant resides has added the arbitration service, and the arbitration service is in the **RUNNING** state.

  * The Locality of the tenant to be enabled for arbitration service is 2F (F: full-featured replica) or 4F.

  * The remaining resources on the host where the arbitration service resides meet the resource requirements.

    You can modify the resource requirements in the system parameters based on your actual needs. The parameters to modify are as follows. For more information, see [Modify a system parameter](../../700.tenant-functions/1600.manage-tenant-parameters/200.modify-a-tenant-parameter.md).

    * `ocp.arbitration.min.remain.disk.size`: The minimum remaining size of the CLOG disk on the arbitration service host when enabling tenant arbitration, in MB. The data format (a,b) represents the values for tenants with 2F and 4F replicas, respectively. The default value is [12,24].
    * `ocp.arbitration.max.cpu.used.percentage`: The maximum CPU usage of the arbitration service host when enabling tenant arbitration, in %. The default value is 90.
    * `ocp.arbitration.max.memory.used.percentage`: The maximum memory usage of the arbitration service host when enabling tenant arbitration, in %. The default value is 90.

* If the primary tenant's cluster has enabled SSL link encryption and the primary-standby synchronization method is **Network-based**, the standby tenant's cluster must also enable SSL link encryption, and the root certificate must be consistent with that of the primary tenant's cluster.

## Procedure

* **Method 1**: Log in to the OCP console, click **<UI-TERM key="ocp-v2.Tenant.New.NewTenant">Create Tenant</UI-TERM>** in the upper-right corner of the **<UI-TERM key="ocp-v2.src.constant.information.Tenant">Tenant</UI-TERM>** page.
