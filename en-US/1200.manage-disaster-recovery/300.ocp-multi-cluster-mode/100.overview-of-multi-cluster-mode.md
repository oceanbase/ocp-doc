# Overview of multi-cluster mode

OCP supports multi-cluster mode, enabling a high-availability disaster recovery architecture across two IDCs. This provides you with more reliable cluster management and monitoring services.

<main id="notice" type='notice'>
<h4>Applicability</h4>
<p>This topic applies only to OCP Enterprise Edition. OCP Community Edition does not support this feature. </p>
</main>

## Overview

The OCP multi-cluster mode is designed for OceanBase disaster recovery across regions. It provides centralized management of primary and standby databases across different regions. This mode supports comprehensive operations management throughout the entire operational lifecycle, including key operations such as primary and standby database creation, decoupling, upgrades, routine switchover, and disaster recovery drills. This ensures business continuity and data security.

The multi-cluster management feature of OCP mainly focuses on unified disaster recovery management across OCP clusters. Its core role is to synchronize the topology information between primary and standby databases, ensuring that a rapid disaster recovery switch and business restoration can be performed in case of a failure at the IDC level. It should be noted that this feature does not automatically take over the resources managed by the primary OCP cluster. If the primary OCP cluster fails, the standby OCP cluster does not automatically take over the OceanBase cluster resources managed by the primary OCP cluster.

<main id="notice" type='explain'>
<h4>Note</h4>
<p>Before V4.1.0, OceanBase Database is a primary-standby cluster. Starting from V4.1.0, OceanBase Database supports tenant-level primary and standby, that is, the primary and standby roles are assigned to tenants. This means that each tenant can be designated as primary or standby. The cluster itself no longer has primary/standby roles, and is only the container that hosts tenants.</p>
</main>

## Architecture of the multi-cluster mode

The OCP multi-cluster disaster recovery switching feature is primarily used in scenarios such as cross-city dual data centers and cross-city triple data centers. The principle is as follows:

### Cross-city dual data centers

When the primary and standby OceanBase clusters are deployed in two cities, you can deploy OCP clusters in two IDCs across these two cities. When the OCP cluster in one city and the OceanBase cluster managed by it fail, the OCP cluster in the other city switches to be the leader and manages the operation, maintenance, monitoring, and alerts of the OceanBase cluster.

The primary and standby OCP clusters are deployed in City 1 and City 2, respectively. The OCP cluster in City 1 is the primary cluster, and the OCP cluster in City 2 is the standby cluster. Each OCP cluster manages multiple OceanBase clusters.

When a network failure causes the connection between the two cities to be interrupted, you can perform a disaster recovery switch to switch the OCP cluster in City 2 to the primary cluster. At this point, the original primary OCP cluster in City 1 becomes an independent and obsolete cluster. It is recommended to delete this obsolete cluster and set up a new primary cluster in City 1. The primary OCP cluster in City 2 will continue to perform operations and maintenance and monitoring on the OceanBase database. For standby databases whose primary database is not managed by this cluster, it will perform disaster recovery switching or migration, as described in [Switch an OCP cluster in a failover](600.switch-an-ocp-cluster-in-a-failover.md).

For OceanBase clusters of versions earlier than V4.1.0, the application accesses an OceanBase cluster through OBProxy. For the primary and standby OceanBase clusters that are managed across OCP clusters, each OceanBase cluster is bound to an OBProxy. You can access a standby OceanBase cluster through the OBProxy bound to it. When the leader and follower OCP clusters fail, the application can still access a standby OceanBase cluster through the OBProxy bound to it.

<main id="notice" type='explain'>
<h4>Note</h4>
<p>If an OBProxy is bound only to a standby OceanBase cluster, you must add the standby cluster ID to the username when you access the standby cluster through the OBProxy, for example, <code>mysql -h xxx.xxx.xxx.xxx -P 2881 -u root@tenant#obcluster:1000 -p ****</code>. The cluster ID is also displayed in the connection string of the OCP cluster. If the ID is removed, you cannot connect to the standby OceanBase cluster.</p>
</main>

After the network is restored, the two primary clusters continue to operate independently. You can set one of the primary clusters as the standby cluster and bind the two clusters by registering the OCP cluster, as described in [Register an OCP cluster](200.register-an-ocp-cluster.md).

### Cross-city triple data centers

In a cross-city triple data center scenario, OCP clusters are deployed in City 1 and City 2, respectively. The OCP cluster in City 1 is the primary cluster, and the two OCP clusters in City 2 are the standby clusters. Each OCP cluster manages multiple OceanBase clusters.

When a network failure causes the connection between the two cities to be interrupted, you can perform a disaster recovery switch to switch one of the standby OCP clusters to the primary cluster. At this point, there is one primary OCP cluster in City 1 and one primary OCP cluster and one standby OCP cluster in City 2.

Each leader OCP cluster monitors the operation and maintenance of the primary OceanBase database managed by it. You must delete the data of the standby OceanBase database whose primary database is not managed by the OCP cluster of the current leader. For more information, see [Switch an OCP cluster in a failover](600.switch-an-ocp-cluster-in-a-failover.md).

For OceanBase clusters of versions earlier than V4.1.0, the application accesses an OceanBase cluster through OBProxy. For the primary and standby OceanBase clusters that are managed across OCP clusters, each OceanBase cluster is bound to an OBProxy. You can access a standby OceanBase cluster through the OBProxy bound to it. When the leader and follower OCP clusters fail, the application can still access a standby OceanBase cluster through the OBProxy bound to it.

<main id="notice" type='explain'>
<h4>Note</h4>
<p>If an OBProxy is bound only to a standby OceanBase cluster, you must add the standby cluster ID to the username when you access the standby cluster through the OBProxy, for example, <code>mysql -h xxx.xxx.xxx.xxx -P 2881 -u root@tenant#obcluster:1000 -p ****</code>. The cluster ID is also displayed in the connection string of the OCP cluster. If the ID is removed, you cannot connect to the standby OceanBase cluster.</p>
</main>

After the network is restored, the standby database of City 2 will appear in the list of OCP clusters in City 1. However, the primary database of this standby database is the primary cluster in City 2. You can unbind the standby database and remove it, as described in [Delete an OCP cluster](700.delete-an-ocp-cluster.md).

If you want to rejoin the original primary cluster to the OCP cluster, you need to clear the data in the original primary cluster.
