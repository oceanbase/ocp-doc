# ob_cluster_no_frozen

## Alert description

This alert monitors whether an OceanBase cluster in OCP has not been frozen for a long time. If the time since the last freeze exceeds the threshold (default value: 90000s), the alert is triggered.

## Alert principle

The following table describes the key parameters involved in the monitoring logic of this alert.

|   Parameter      |       Value       |
|-------------|-------------|
| Monitoring metric    | no_frozen_time, which indicates the time since the last freeze. If the value of this metric exceeds the threshold, the alert is triggered.     |
| Monitoring expression  | ```(max(ob_zone_current_timestamp{name="frozen_time",@LABELS}) by (@GBLABELS) - max(ob_zone_stat{name="frozen_time",@LABELS}) by (@GBLABELS)) / 1000000```      |
| Collected metrics    | ob_zone_current_timestamp, ob_zone_stat      |
| Metric source    | Internal views. SQL statement: ```select /*+ MONITOR_AGENT READ_CONSISTENCY(WEAK) */ zone, name, value, time_to_usec(now()) as current from __all_zone``` |
| Collection cycle    | 5 seconds    |

## Rule information

|         Monitoring metric             | Default threshold (unit: seconds) | Duration | Detection cycle | Elimination cycle |
|------------------------------|------------|-------|------|------|
| no_frozen_time               | 90000      | 0 seconds  | 10 seconds | 5 minutes |

## Alert information

|   Trigger method   | Alert level | Scope |
|------------|------|-------|
| Based on the expression of the monitoring metric | Critical   | Cluster |

## Alert template

* **Alert overview**

  * Template: \${alarm_target} \${alarm_name}
  * Example: alarm_template_id=0:ob_cluster=obcluster-1 OceanBase cluster has not been frozen for a long time

* **Alert details**

  * Template: Cluster: \${ob_cluster_name}, Alert: \${alarm_name}. The time since the last freeze is \${value_shown} seconds, which exceeds ${alarm_threshold} seconds.
  * Example: Cluster: obcluster-1, Alert: OceanBase cluster has not been frozen for a long time. The time since the last freeze is 1 hour 17 minutes 49.496 seconds, which exceeds 40 seconds.

* **Alert recovery**

  * Template: Alert: ${alarm_name}. The time since the last freeze is: \${value_shown} seconds.
  * Example: Alert: OceanBase cluster has not been frozen for a long time. The time since the last freeze is: 70000.0 seconds.

## Impact on the system

If the cluster does not initiate a major compaction or a major freeze for a long time, the disk space will increase, and the disk may be full, which will affect the business write.

## Possible causes

* Daily major compactions are disabled, or the upgrade mode parameter is enabled.

* The Root Service is abnormally paused, such as when there is no leader or when the process is abnormally paused.

## Solution

1. Check whether daily major compactions are enabled. On the **<UI-TERM key="ocp-v2.Compaction.Settings.MergePolicy">Major Compaction Strategy</UI-TERM>** page of the **<UI-TERM key="ocp-v2.Cluster.Overview.Compaction">Compaction Management</UI-TERM>** section of the **<UI-TERM key="ocp-v2.Cluster.Overview">Overview</UI-TERM>** page of the OCP console, check whether **<UI-TERM key="ocp-v2.Compaction.Settings.DailyMergeTime">Major Compaction Time</UI-TERM>** is configured.

   * If not configured, the cluster will not automatically trigger a major freeze. You must manually enable it.

   * If configured, the issue may be due to other reasons. Proceed to the next step.

2. Check whether the Root Service is abnormally paused due to an abnormal process.

   If the observer process is abnormal, the alert [ob_cluster_exists_inactive_server OB cluster has an inactive OBServer node](../200.ob-alert/400.ob_cluster_exists_inactive_server.md) will also be triggered. You can first refer to the documentation to handle the issue and then observe whether the alert is still triggered after 5 minutes.

3. Check whether the Root Service has no leader.

   Execute the following statement to query the `__all_virtual_core_meta_table` table and determine whether the Root Service has no leader.

   ```sql
   -- Query the sys tenant.
   SELECT svr_ip, zone, role, member_list FROM __all_virtual_core_meta_table;
   ```

   * If the connection is normal but the query fails, the Root Service has no leader.

     You can try to restart the OBServer node where the Root Service is located or restart all OBServer nodes in the rootservice_list to restore the Root Service.

     1. Use the following method to find the IP address of the corresponding OBServer node.

        ```sql
        -- Query the sys tenant.

        -- Query the OBServer node where the Root Service is located.
        SELECT zone, svr_ip, svr_port
        FROM __all_server WHERE with_rootserver=1;

        -- Query the rootservce list.
        -- The rootservice_list is a string separated by semicolons. Each part represents an OBServer node.
        SELECT DISTINCT `value` AS rootservice_list
        FROM __all_virtual_sys_parameter_stat
        WHERE `name` = 'rootservice_list';
        ```

     2. In the **<UI-TERM key="ocp-v2.Component.OBServerList.ObserverList">OBServers</UI-TERM>** section of the **<UI-TERM key="ocp-v2.Detail.Monitor.Monitor.Overview">Overview</UI-TERM>** page of the cluster, click the **<UI-TERM key="ocp-v2.src.constant.compute.Restart">Restart</UI-TERM>** button of the corresponding OBServer node.

    <main id="notice" type='explain'>
    <h4>Note</h4>
    <p>If you choose to forcibly restart, the process will be directly terminated. This method is required when the majority of nodes are not available. Restarting an OBServer node when the majority of nodes are not available will result in some replicas having no leader. After the restart, you may need to wait 15 minutes before the sys tenant can connect. Business tenants will also experience similar issues.</p>
    </main>

     3. If the Root Service is still not restored after the restart or after waiting for 15 minutes, proceed to step 3.

   * If the Root Service has a leader, the issue may be due to other reasons. Proceed to step 4.

4. Collect the log information from the OBServer node and contact technical support for analysis and resolution.
