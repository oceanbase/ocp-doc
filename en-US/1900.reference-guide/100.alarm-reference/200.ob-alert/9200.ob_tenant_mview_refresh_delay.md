# ob_tenant_mview_refresh_delay

## Alert description

<main id="notice" type='explain'>
<h4>Note</h4>
<li>This alert is applicable only to OceanBase clusters of V4.3.5.0 and later. </li>
<li>When a primary-standby relationship exists between tenants, only the primary tenant can report this alert. </li>
</main>

This alert monitors whether materialized views in the database of the tenant are refreshed in a timely manner. If the refresh is delayed, the alert is triggered.

## Alert principle

1. The OCP scheduled task executes the following SQL statement in the sys tenant of all clusters to collect data about the delayed automatic refresh of materialized views. The data is stored in the `sql_aggregate_data` table of the OCP MonitorDB. The scheduled task is executed every 60 seconds.

   ```sql
    SELECT E.tenant_id, E.tenant_name, A.database_name, B.table_name AS mview_name, C.last_refresh_date, D.next_date
    FROM oceanbase.__all_virtual_database A, oceanbase.__all_virtual_table B, oceanbase.__all_virtual_mview C, oceanbase.__all_virtual_tenant_scheduler_job D, oceanbase.DBA_OB_TENANTS E
    WHERE A.tenant_id = B.tenant_id
      AND B.tenant_id = C.tenant_id
      AND C.tenant_id = D.tenant_id
      AND D.tenant_id = E.tenant_id
      AND A.database_id = B.database_id
      AND B.table_id = C.mview_id
      AND C.refresh_job = D.job_name
      AND C.refresh_job IS NOT NULL
      AND D.job != 0
      AND D.next_date < Now()
      AND E.tenant_type <> 'META'
      AND E.tenant_name IS NOT NULL
      AND E.tenant_role = 'PRIMARY';
   ```

2. The OCP alert detection task identifies whether the alert item is of the SQL_AUDIT type. If it is, the following command is executed to scan for abnormal data in the `sql_aggregate_data` table. Corresponding alerts are generated based on the alert detection rules.

   ```sql
   select * from sql_aggregate_data where tags like '%mview_stat%' order by timestamp desc
   ```

## Rule information

| Metric | Default threshold | Duration | Detection cycle | Elimination cycle  |
|----------|----------|---------|----------|-----------|
| NA       | NA       | 0 seconds    | NA       | 5 minutes  |

## Alert information

| Trigger method | Alert level | Scope  |
|--------------|---------|--------|
| Triggered by a scheduled task | Warning | Tenant  |

## Alert template

* **Alert overview**

  * Template: ${alarm_target} ${alarm_name}
  * Example: alarm_template_id=0:ob_cluster=test471-11:tenant_name=mysqlTes:database=test:mview_name=test_mv_refresh_retry_mv2 Materialized view refresh is delayed

* **Alert details**

  * Template: The automatic refresh of the materialized view ${mview_name} in the database ${database} of the tenant ${tenant_name} in the OceanBase cluster ${ob_cluster_name} is delayed. The expected refresh time is ${next_date}.
  * Example: The automatic refresh of the materialized view test_mv_refresh_retry_mv2 in the database test of the tenant mysqlTes in the OceanBase cluster test471 is delayed. The expected refresh time is 2025-11-14T16:13:55.026383+08:00.

## Impact on the system

The timeliness of materialized views cannot be guaranteed.

## Possible causes

Too much incremental data or an inefficient refresh plan.

## Solution

1. Execute the following command as the sys tenant to query sessions related to materialized views:

    ```sql
    select id, svr_ip, svr_port,tenant_id, time, info
    from oceanbase.__all_virtual_processlist
    where info like '%mview_name%'\G
    ```

    In the `mview_name` parameter, specify the name of the materialized view that is in an abnormal state.

2. If there are sessions that have been running for a long time, view the currently executing plans:

    ```sql
    select dbms_xplan.display_active_session_plan(id, 'all', svr_ip, svr_port)\G
    ```

    In the `id`, `svr_ip`, and `svr_port` parameters, specify the values obtained from the previous step.

3. Analyze the plan information to troubleshoot the issue of prolonged refresh time. If necessary, contact OCP technical support for assistance.
