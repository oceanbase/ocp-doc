# tenant_cpu_percent_over_threshold OceanBase tenant CPU usage exceeds threshold

## **Alert description**

This alert is triggered when the OceanBase tenant thread usage exceeds the specified threshold.

OceanBase tenant thread usage = (Number of tenant threads actually in use) / (Sum of tenant thread limits across all units in the tenant's primary zone).

## Alert principle

The following table lists the key parameters involved in the monitoring logic of this alert.

| Parameter  | Value                     |
|-------|------------------------|
| Monitoring metric  | ob_tenant_thread_percent <main id="notice" type='explain'><h4>Note</h4><p>This metric indicates the thread usage of tenants in the cluster. An alert is triggered when this value exceeds the threshold (default is 95%).</p></main>        |
| Metric source  | SQL: `select /*+read_consistency(weak)*/ tenant_name, tenant_id, stat_id, value from v$sysstat, __all_tenant where stat_id IN (140006, 140005) and (con_id > 1000 or con_id = 1) and __all_tenant.tenant_id = v$sysstat.con_id; `  </br> sysstat_value takes the value from the value field, and other fields serve as labels.                    |
| Metric to be collected  | sysstat_value         |
| Monitoring expression | 100 \* sum(sysstat_value{metric_group="sysstat",stat_id="140006",@LABELS}) by (@GBLABELS) / sum(sysstat_value{metric_group="sysstat",stat_id="140005",@LABELS}) by (@GBLABELS)  <ul><li> For event ID 140005: calculates the maximum number of threads available to the tenant. </li><li> For event ID 140006: calculates the number of threads currently in use by the tenant. </li></ul>   The monitoring expression in the table indicates that the ratio of the sum of values for "stat_id=140006" to the sum of values for "stat_id=140005" is used as the tenant thread usage metric. |
| Collection interval  | 1 second                   |

## **Impact on the system**

None.

## **Possible causes**

* A large query or hot data was generated.

* The tenant resource plan was smaller than the actual resources, and an unexpected hot scenario occurred.

## **Procedure**

1. Check whether the load is normal.

   Log in to the OCP console and go to the **<UI-TERM key="ocp-v2.page.Monitor.PerformanceMonitoring">Performance Monitoring</UI-TERM>** page of the tenant. On the **Performance and SQL** tab, view the **<UI-TERM key="ocp-v2.src.constant.monitor.TenantThreadUsage">Thread Usage of Tenant</UI-TERM>** line chart. If the tenant thread usage suddenly increased at the alert time point compared with the past 1-7 days, the load is abnormal.

   * If yes, the load is abnormal.

   * If no, the load is normal.

     If the normal traffic caused the load to be too high, increase the tenant specification by referring to [Manage tenant specifications](../../../700.tenant-functions/1630.manage-unit-specification.md) to allocate more tenant thread resources.

2. The high load may be caused by a large query or hot traffic.

   You can handle it based on the following scenarios.

   * A large query exists in the SQL execution.

     On the **TopSQL** tab of the **<UI-TERM key="ocp-v2.page.Overview.SqlDiagnosis">SQL Diagnostics</UI-TERM>** page in the OCP console, view whether there is an SQL statement that uses a high amount of CPU resources.

     * If yes, you can optimize the SQL statement.

     * If no, the cause is not this one.

   * SlowSQL causes the high load.

     On the **SlowSQL** tab of the **<UI-TERM key="ocp-v2.page.Overview.SqlDiagnosis">SQL Diagnostics</UI-TERM>** page in the OCP console, view the specific diagnostic results and analyze whether it may cause the tenant thread load to be too high.

     If yes, you can optimize the SQL statement.

   * The hot data caused by hot rows leads to a high CPU usage of a tenant node. If this is the case, you can limit the traffic of the tenant business by referring to [Limit the traffic of OceanBase cluster](../500.appendix/200.limit-the-inbound-traffic-of-the-oceanbase-cluster.md).
