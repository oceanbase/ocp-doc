# os_observer_not_exist OceanBase server process does not exist

## Alert Description

This alert monitors whether the observer process is running on the OBServer host. If the observer process is not running, the alert is triggered.

## Alerting Principles

| Parameter | Value |
| --- | --- |
| Monitoring indicator | observer_process_exists |
| Monitor Source | Basic monitoring of host systems, check if the observer process is running </br>Run the command `ps -ef|grep -w observer|grep -v grep|wc -l` to return the number of observer processes. |
| Collection metric | process_exists |
| Monitoring expression | min(process_exists{name="observer",@LABELS}) by (@GBLABELS) |
| Sampling Interval | 1 sec |

## Rule Information

| Monitoring expression | Description | Default threshold | Detection interval | Elimination interval |
| --- | --- | --- | --- | --- |
| observer_process_exists == 0 | <li>0: The process does not exist.</li><li>1: The process exists.</li> | 0 | 10 seconds | 5 minutes |

## Alert information

| Alert Trigger Method | Alert Level | Scope |
| --- | --- | --- |
| Expression based on monitoring metrics | Severity | Server |

## Alert template

* Alert Summary
  * Template: \${alarm_target} ${alarm_name}
  * Example: obcluster=obcluster-1631964370:svr_ip=xxx.xxx.xxx.xxx OceanBase server process does not exist
* Alert details
  * Template: cluster: \${ob_cluster_name}, host: ${host}, alert: OceanBase server process does not exist.
  * Sample: Cluster: obcluster-1, Host: xxx.xxx.xxx.xxx, Alert: OceanBase server process does not exist.
* **Alert restore**
  * Template: Alert: ${alarm_name}, OceanBase server process status: \${recover_value}
  * Example: Alert: OceanBase server process does not exist, OceanBase server process status: 1

## Impact on the system

* For a single-replica system, the absence of observer processes would result in the service being halted.
For a multi-replica OceanBase cluster, the availability may decrease because the observer process does not exist: for example, 3 zones to 2 zones or 3 IDCs within a region to 2 IDCs.

## Possible Causes

The OBServer node is unexpectedly restarted, for example, when it is killed due to insufficient system resources.

## Treatment Method

1. Attempt to restore the observer process when it unexpectedly exits. You can execute an alert action plan to resolve the issue. For more information, see [Alert action plans](../500.appendix/400.execute-the-plan.md).

   <main id="notice" type='explain'>
     <h4>The event was triggered only once within the 30 minutes before the event occurred.
     <p></p>
   </main>

2. Check if the host's basic monitoring metrics, such as memory usage, CPU utilization, load, and disk usage, meet the expected standards.

3. Check if there are a large number of ERROR logs in the OBServer node logs:

    ```yaml
    tail -10000 /home/admin/oceanbase/log/observer.log.wf | grep ERROR | wc -l
    ```

    If there are many ERROR logs, contact technical support.

4. Check the OS log and search for the error keyword in the `/var/log/messages` log file to observe the system response.
