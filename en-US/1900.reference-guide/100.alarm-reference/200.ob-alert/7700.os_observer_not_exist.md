# os_observer_not_exist OceanBase server process does not exist

## Alert Description

This alert monitor checks whether the observer process is running on the OBServer host. If not, an alert is generated.

## Alerting concept

| Parameter | Value |
| --- | --- |
| Monitoring Metric | observer_process_exists |
| Monitoring Source | Monitoring of basic host features to check if there are observer processes in the system. </br>You can run the `ps -ef|grep -w observer|grep -v grep|wc -l` command to view the number of observer processes. |
| Collected metric | process_exists |
| monitoring expression | min(process_exists{name="observer",@LABELS}) by (@GBLABELS) |
| Sampling Interval | 1 sec |

## Rule information

| Monitoring Expression | Meaning of the Monitoring Metric | Default Threshold | Detection Cycle | Elimination Cycle |
| --- | --- | --- | --- | --- |
| observer_process_exists == 0 | <li>0: The process does not exist.</li><li>1: The process exists.</li> | 0 | 10 seconds | 5 minutes |

## Alert message

| Alert Trigger Method | Alert Level | Scope |
| --- | --- | --- |
| Expression based on monitoring metrics | Critical | Server |

## Alert Template

* Alarm Overview
  * Template: \${alarm_target} ${alarm_name}
  * Sample: obcluster=obcluster-1631964370:svr_ip=xxx.xxx.xxx.xxx: OceanBase server process does not exist
* Alert Details
  * Template: Cluster: \${ob_cluster_name}, Host: ${host}, Alert: OceanBase server process does not exist.
  * Sample: Cluster: obcluster-1, Host: xxx.xxx.xxx.xxx, Alert: OceanBase server process does not exist.
* **Alert restored**
  * Template: Alarm: ${alarm_name}, OceanBase server process survival status: \${recover_value}
  * Example: Alert: OceanBase server process does not exist, OceanBase server process status: 1

## Impact on the system

* In a single-replica system, the absence of observer processes can result in service termination.
For multi-replica OceanBase clusters, the availability may decrease if the observer process is absent: for example, from 3 zones to 2 zones, or from three local IDCs to two local IDCs.

## Potential causes

The OBServer node was unexpectedly restarted, for example, when it was killed due to insufficient system resources.

## How to do it

1. You can try to restore the observer process if it unexpectedly exits. You can quickly handle it by executing the alert action plan. For more information, see [Action plan](../500.appendix/400.execute-the-plan.md).

   <main id="notice" type='explain'>
     The event was triggered only once within the 12 hours.
     <p></p>
   </main>

2. Check the host's baseline monitoring metrics, including memory usage, CPU utilization, load, and disk usage, to ensure they meet expectations.

3. Check if there are many error logs in the running log of the OBServer node:

    ```yaml
    tail -10000 /home/admin/oceanbase/log/observer.log.wf | grep ERROR | wc -l
    ```

    If there are a large number of error logs, contact technical support.

4. Check the OS logs, search for the error keyword in the `/var/log/messages` log file, and observe the system's returned information.
