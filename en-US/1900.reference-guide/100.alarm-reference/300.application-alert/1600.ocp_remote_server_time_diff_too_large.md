## Alert description

This alert monitors the clock synchronization between the OCP server and a remotely managed host. If the clock deviation exceeds the threshold, the alert is generated.

## Alert principle

OCP-Server sets a scheduled task to run the `clockdiff -o {ip}` command every minute. The task checks the clock drift of a remote host and triggers an alert when the drift exceeds the threshold set by the system parameter `ocp.host.check.clock-diff.max-diff`, which defaults to 50 milliseconds. </think>  OCP-Server sets a scheduled task to run the `clockdiff -o {ip}` command every minute.   * Template: \${alarm_target} \${alarm_name}
  * Examples: alarm_template_id=0:host=xxx.xxx.xxx.xxx OCP time difference with the remote host is too large.

* **Alert details**

  * Template: The time difference between the OCP service and the remote host ( ${host} in the ${ob_cluster_name} cluster) is too large. The current time difference is ${value_shown} milliseconds, which is greater than the threshold value of ${alarm_threshold}.
  * Sample: The time difference between OCP and the remote host (xxx.xxx.xxx.xxx, which belongs to the obcluster-1 cluster) is too large. The current time difference is 1400 milliseconds, which exceeds the threshold of 50 milliseconds.

* **Alert recovery**

  * Template: ${alarm_target}. Clock offset between the host and OCP-Server: ${value_shown}
  * Example: The time difference between OCP and the remote host is 1,400 ms, which is larger than the maximum of 50 ms.

## **Impact on the system**

* RPC request failed.

* The authorization fails.

* Queries for some metrics fail.

## Possible causes

Common reasons:

* The time of the OCP server is incorrect.

* The clock of the remote host is out of sync.

## Solution

Check whether the clock of the OCP server is normal.

   Check whether the OCP has reported the same alert multiple times.

   * Otherwise, proceed to step 2.

   - Yes, the OCP server has a clock error.

     Ensure that the clock of the OCP server is working properly.

     It is likely that there is an issue with the clock synchronization between the OCP server and the NTP server. For more information, see [host_ntp_offset_too_large](../300.application-alert/2000.host_ntp_offset_too_large.md).

     Wait 5 minutes to see whether the alarm continues to be reported.

2. Check whether the time on hosts managed by OCP is correct.

   * When the host managed by OCP is unavailable or not connected, the following alerts are also reported. You can first refer to the document to resolve the following alerts, manually trigger the host to synchronize the time with the clock source, and wait for 5 minutes to observe whether the alert is still reported.

     * [OB server cannot be connected](../200.ob-alert/100.ob_cannot_connected.md)

     * [ob_cluster_exists_inactive_server](../200.ob-alert/400.ob_cluster_exists_inactive_server.md)

   * The time sync between the host managed by OCP and the clock source may have been abnormal. For more information, see [host_ntp_offset_too_large](../300.application-alert/2000.host_ntp_offset_too_large.md).

   * If the OCP server and host have no abnormal clocks but are out of synchronization, you can manually trigger clock synchronization.

     Select one of the following commands based on the NTP server configuration.
