# ob_cluster_no_frozen OceanBase 集群长时间未冻结

## 告警描述

该告警监测 OCP 中的 OceanBase 集群是否长时间未触发冻结，距离上一次冻结时间超过阈值（默认为 90000s）则触发告警。

## 告警原理

下表列出了该告警监控逻辑中涉及的关键参数。

|   参数      |       值       |
|-------------|-------------|
| 监控指标    | no_frozen_time，该指标表示集群有未执行冻结的时间，当指标值大于阈值时触发告警。     |
| 监控表达式  | ```(max(ob_zone_current_timestamp{name="frozen_time",@LABELS}) by (@GBLABELS) - max(ob_zone_stat{name="frozen_time",@LABELS}) by (@GBLABELS)) / 1000000```      |
| 采集指标    | ob_zone_current_timestamp、ob_zone_stat      |
| 指标来源    | 采集自内部视图，采集 SQL：```select /*+ MONITOR_AGENT READ_CONSISTENCY(WEAK) */ zone, name, value, time_to_usec(now()) as current from __all_zone``` |
| 采集周期    | 5 秒    |

## 规则信息

|         监控指标             | 默认阈值（单位：秒） | 持续时间 | 检测周期 | 消除周期 |
|------------------------------|------------|-------|------|------|
| no_frozen_time               | 90000      | 0 秒  | 10 秒 | 5 分钟 |

## 告警信息

|   告警触发方式   | 告警等级 | 范围 |
|------------|------|-------|
| 基于监控指标的表达式 | 严重   | 集群 |

## 告警模板

* **告警概述**

  * 模板：\${alarm_target} \${alarm_name}
  * 样例：alarm_template_id=0:ob_cluster=obcluster-1 OceanBase 集群冻结检测失败

* **告警详情**

  * 模板：集群：\${ob_cluster_name}，告警：\${alarm_name}。距上一次冻结时间为 \${value_shown} 超过 ${alarm_threshold} 秒。
  * 样例：集群：obcluster-1，告警：OceanBase 集群冻结检测失败。距上一次冻结时间为 90001.0 秒超过 90000.0 秒。

* **告警恢复**

  * 模板：告警：${alarm_name}，OceanBase 集群距离上一次冻结的间隔：\${value_shown} 秒
  * 样例：告警：OceanBase 集群冻结检测失败，OceanBase 集群距离上一次冻结的间隔：70000.0 秒

## 对系统的影响

长时间不发起冻结或合并会导致磁盘空间增大，磁盘爆满，影响业务写入。

## 可能原因

* 每日合并被关闭或升级模式参数开启。

* Root Service 服务异常暂停，比如无主，或者进程异常暂停。

## 处理方法

1. 检查是否开启了每日合并。在 OCP **集群概览 \> 合并管理 \> 合并配置** 页面的 **<UI-TERM key="ocp-v2.Compaction.Settings.MergePolicy">合并策略</UI-TERM>** 中是否配置了 **<UI-TERM key="ocp-v2.Compaction.Settings.DailyMergeTime">每日合并时间</UI-TERM>** 。

   * 未配置，则不会自动冻结触发，需请手动打开。

   * 已配置，则可能是其他原因 ，请继续执行下一步。

2. 检查是否进程异常导致 Root Service 服务异常。

   若 observer 进程异常，则会有 [ob_cluster_exists_inactive_server OB 集群存在不工作 OBServer 节点](../200.ob-alert/400.ob_cluster_exists_inactive_server.md) 同时上报，可先参考文档处理后，再观察 5min 后，告警是否还上报。

3. 检查 Root Service 是否无主。

   执行如下语句查询 `__all_virtual_core_meta_table` 判断 Root Service 是否无主。

   ```sql
   -- 连接 sys 租户 查询
   SELECT svr_ip, zone, role, member_list FROM __all_virtual_core_meta_table;
   ```

   * 如果连接正常，但是查询失败，说明 Root Service 处于无主状态。

     可通过重启 Root Service 所在的 OBServer 节点尝试恢复，或者重启 rootservice_list 中的所有的 OBServer 节点尝试恢复。

     1. 通过如下方法找到对应 OBServer 节点的 IP。

        ```sql
        -- 连接 sys 租户查询

        -- 查询 Root Service 所在 OBServer 节点
        SELECT zone, svr_ip, svr_port
        FROM __all_server WHERE with_rootserver=1;

        -- 查询 rootservce list
        -- rootservice_list 的格式为 ';' 分隔的字符串，每个部分表示 一台 OBServer 节点
        SELECT DISTINCT `value` AS rootservice_list
        FROM __all_virtual_sys_parameter_stat
        WHERE `name` = 'rootservice_list';
        ```

     2. 在集群 **<UI-TERM key="ocp-v2.Detail.Monitor.Monitor.Overview">总览</UI-TERM>** 界面的 **<UI-TERM key="ocp-v2.Component.OBServerList.ObserverList">OBServer 列表</UI-TERM>** 中单击对应 OBServer 节点的 **<UI-TERM key="ocp-v2.src.constant.compute.Restart">重启</UI-TERM>** 按钮。

    <main id="notice" type='explain'>
    <h4>说明</h4>
    <p>选择强制重启，会以直接结束进程的方式重启，当不满足多数派时，需采用此方式重启。不满足多数派时重启 OBServer 节点会导致部分副本无主，重启后可能需要等待 15 分钟后 sys 租户才可以连接，业务租户也会有同样的情况发生。</p>
    </main>

     3. 重启之后或强制重启等待 15 分钟之后仍然没有恢复，请执行步骤 3。

   * 如果有主，则可能是其他原因，请执行步骤 4。

4. 请收集 OBServer 节点上的日志信息，联系技术支持分析解决。
