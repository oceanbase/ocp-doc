# tenant_all_unit_server_not_connectable OceanBase 租户无法连接

## 告警描述

OBProxy V4.3.3.0 开始支持基于租户服务名的读写分离。OBProxy 请求 OCP Server 获取所有租户的服务名信息，对同一个服务名下的主备租户实现读写分离。当备租户不可用时，由于 OCP 无法感知，仍将备租户服务名返回给 OBProxy，OBProxy 持续将 SQL 读请求路由到备租户，导致业务读持续发生读请求失败。

针对上述场景，OCP 需要涉及并实现一个预案，实现如下能力：

1. 可检测到备租户不可用。
2. 备租户不可用时，将该备租户从返回给 OBProxy 的服务名信息中摘除，避免 OBProxy 再路由到该备租户。

预案是基于告警触发的，此告警仅针对上述预案场景，对配置预案的备租户进行连接性检查，若判断租户不可连接，则发起告警。

## 告警原理

此告警的前提条件如下：

1. 租户为备租户。
2. 租户配置了 `租户服务名信息中删除探活失败租户` 预案。
3. 租户的服务名为 VALID 状态。

下表列出了该告警监控逻辑中涉及的关键参数。

| 参数 | 值  |
|------|------|
| 监控指标 | ob_tenant_any_unit_connectable  |
| 数据来源 | OCP 定时任务检查租户的 Unit Server 状态，所有 Unit Server 端口连接失败则判断租户不可连接，记录 `ob_tenant_any_unit_connectable = 0`，否则 `ob_tenant_any_unit_connectable = 1`  |
| 采集指标（单位：秒） | ob_tenant_any_unit_connectable  |
| 监控表达式 | max(ob_tenant_any_unit_connectable{@LABELS}) by (@GBLABELS)  |
| 采集周期 | 60 秒  |
| 监控指标  | ob_tenant_any_unit_connectable 的值只有 0 或者 1，1 表示租户可以连接，0 表示不可连接。  |

## 规则信息

| 监控指标 | 默认阈值 | 持续时间 | 检测周期 | 消除周期  |
|------|------|------|------|------|
| ob_tenant_any_unit_connectable | 1 | 0 秒 | 60 秒 | 5 分钟  |

## 告警信息

| 告警触发方式 | 告警等级 | 范围  |
|------|------|--------|
| 基于监控指标的表达式 | 严重 | OCP  |

## 告警模板

* **告警概述**

  * 模板：${alarm_target} ${alarm_name}
  * 样例：larm_template_id=0:ob_cluster=ob4353-22:tenant_name=jilian_standby_tenant OceanBase租户无法连接。

* **告警详情**

  * 模板：集群：${ob_cluster_name}，租户：${tenant_name}，告警：${alarm_name}。租户所有 UNIT 节点 SQL 端口均连接失败。
  * 样例：OceanBase cluster: ob4353，tenant: jilian_standby_tenant，alert: OceanBase 租户无法连接。租户所有 UNIT 节点 SQL 端口均连接失败。

* **告警恢复**

  * 模板：告警：${alarm_name}，OceanBase 租户 UNIT 是否可连接：\${recover_value}
  * 样例：告警：OceanBase 租户无法连接，OceanBase 租户 UNIT 是否可连接：1

## 对系统的影响

* 对 OCP 的影响：OCP 发起预案，将该租户的从服务名下删除，让 OBProxy 对其不可见。
* 对 OBProxy 的影响：OBProxy 不可见该租户，会将读流量从该租户切走，切到同服务名的其它租户下。
* 对应用的影响：租户不可连接，可能导致应用无法连接该租户。由于 OBProxy 切流，应用的读流量会被自动打到另一个租户。

## 可能原因

机房故障，导致租户的所有主机宕机。

## 处理方法

1. 用户需自行排查租户异常原因，恢复租户。
2. 恢复租户后，在 OCP 中修改租户的服务名，将其重新改为 VALID 状态，使其对 OBProxy 可见。
